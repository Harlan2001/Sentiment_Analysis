# 策略生成后续优化方向

## 一、我们最初想做什么

就一件事：**让舆情因子真正参与策略生成，而不是当摆设。**

拆开是四条：

1. **因子得能用上**：381 个因子，不能只在页面上列个名字，得真的影响策略怎么开仓；
2. **标的不能让模型自己挑**：它挑错过，在债券平台上做过沪金期货策略，还一笔没成交；
3. **回测结果得可信**：平台认为"跑完就算通过"，零成交也打绿灯，这个绿灯没有意义；
4. **过程得看得懂**：用户不能只看到"通过/不通过"，得知道凭什么。

分工一句话：**我们出决策，它出代码，我们验收。**

---

## 二、已经做了什么

### 2.1 链路已经能跑通

从用户输入一句话，到拿到带回测结果的策略代码，整条路已经打通：

> 提需求 → 整理情报（新闻 + 因子） → 发给对端 → 模型写代码 → 回测 → 我方验收 → 存库 → 页面展示

### 2.2 五项改造

**因子信号面板**：381 个因子里只挑得出 **21 个**真正管用的（要求历史样本够多、命中率跑赢"无脑猜"）。其余放进情报里只会干扰模型。

**策略任务卡**：标的限定在我们指定的 5 个利率债品种里（黄金排除在外，因为我们的因子方向是债市口径，套到黄金上是错的）。同时明确要求"必须真实下单，禁止只打日志"——这是 21 个零成交模板的直接病根。

**验收门**：平台说"通过"不算数，我们自己再判一道。分三步：回测跑完了吗 → 日志里能找到成交笔数吗 → 笔数大于零吗。只有"跑完但没成交"值得重试，其他情况直接把原因告诉用户。

**错误即时可见**：对端报错时立刻返回原因，不再傻等 900 秒超时。

**页面改造**：新增「因子与逻辑」模块，把"凭什么得出这个结论"逐环摊开；策略概要改成结构化展示；回测代码加了语法高亮。

### 2.3 性能没有想象中慢

实测了 12 次调用：

- 服务重启后第一次：0.9 秒
- **连续使用（浏览器的真实情况）：0.6–0.8 秒**
- 自动化脚本每次新建连接：20 秒

那个 20 秒是测试脚本没复用连接造成的，不是服务本身的问题。浏览器里稳定在 0.7 秒左右。

## 三、接下来的优化方向

### 3.1 提示词草稿：能改，也要看得懂

**现在的问题**

提示词是一大段 2978 字的纯文本，用户看到的是：

```
【交易规则与策略需求】
[USER_EDITABLE_REQUIREMENT]
[TRADING_PARAMETERS]
- 开仓规则：5日均线上穿20日均线...
```

三个毛病：一是 `[XXX]` 这种模板标记对用户毫无意义；二是将近 3000 字一屏看不完，不知道哪段能改；三是想改"止损"得在几千字里翻，翻错了还保存不了。

**改法：分段折叠，能改的段标出来**

把提示词按 `【】` 标记切成几块，每块可以折叠：

```
▼ 交易参数与策略需求      [可编辑]  320字
   开仓规则：5日均线上穿20日均线
   止损：1.5%
▼ 策略任务卡（强制）              186字
   交易品种：FCT_T_MAIN
▶ 因子信号面板                    859字
▶ 执行要求                        412字
```

只有"交易参数"那一段能改，其余折叠只读。**编辑还是写回原来那份提示词，后端逻辑一行都不用动**，只是让用户看得清自己在改什么。

另外可以加：改过的段落标个颜色条，确认前能看出自己动了哪里；顶部显示"已用 2823 / 4000 字"，快满了变黄。

### 3.2 策略概要：别光复述我的输入

**现在的问题**

模型返回的概要是这样的：

> 标的：FCT_T_MAIN
> 开仓：5 日均线上穿 20 日均线
> 平仓：5 日均线下穿 20 日均线
> 仓位：20%

**这基本就是把我们下发的任务卡抄了一遍。** 用户看完还是不知道：这策略凭什么值得看？它赌的是什么？什么情况下会亏？

**改法：四层结构**

**第一层，一句话说清楚在干什么**：
> 用 5/20 均线金叉抓趋势，靠因子方向确认避开逆势开仓，死叉或赚够 3% 就走。

**第二层，它赌的是什么**：

| 赌什么 | 具体内容 | 能不能验证 |
|---|---|---|
| 趋势会延续 | 金叉之后能涨 3–10 天 | 回测能验证 |
| 因子方向有用 | 这 6 个多头因子能预测未来方向 | 已有历史研究支撑 |
| 止损够用 | 1.5% 止损能兜住正常回撤 | 回测能验证 |

**第三层，什么时候会亏**（这一层最重要）：
> 震荡市里均线会反复交叉，被来回止损。回测期内死叉平仓 12 次，其中 7 次亏损。

**这句话不是模型说的，是我们自己从回测日志里统计出来的。** 只有这种真实数据才建立得起信任。

**第四层，实现细节**：保留现有的标的、开平仓、仓位、风险这些。

### 3.3 回测指标：从一堆数字变成看得懂

**现在的问题**

28 个指标平铺成卡片，其中真正有用的也就 10 个左右，剩下 18 个（Alpha 全是 0、Tracking Error 是 0、各种哈希值）纯属噪音。

**更要命的是这批数字本身就可疑**：

```
夏普比率     -234.606    ← 明显算错了
年化波动率   0           ← 波动率为 0 哪来的夏普？
两年净利润   0.004%      ← 赚了 36 块钱
胜率         64%         ← 胜率高却不赚钱
```

夏普 -234 是因为波动率趋近于零导致除法爆炸。这种数字摆出来比不摆更伤信任。

**改法一：画图（最有价值）**

回测日志里其实**已经记了每一笔交易**：

```
[20240312] 开多 1552 手 @ 107.3553
[20240326] 平多 1552 手 @ 106.9301 原因=死叉 收益=-0.40%
```

把这些解析出来，就能画：

- **收益曲线**：把每笔收益连起来，这是用户判断策略好坏最直观的东西
- **盈亏柱状图**：每笔赚亏一根柱子，一眼看出是"小亏多次大赚一次"还是"稳定小赚"
- **交易明细表**：开仓日、平仓日、持仓天数、开平价、收益率、平仓原因
- **平仓原因饼图**：死叉/止损/止盈各占多少，反映这策略是靠趋势赚钱还是靠止损活命

数据都是现成的，只是现在埋在文本日志里。

**改法二：指标分层**

```
核心指标（大字）：成交 29 笔 │ 年化 0.001% │ 回撤 0% │ 胜率 64%
收益质量：       盈亏比 0.62 │ 期望 0.043 │ 费用 $0
风险指标：       夏普 -234 ⚠异常 │ 索提诺 -219
其他（折叠）：   18 个技术指标，默认收起
```

那个算错的夏普，与其正正经经摆在卡片里，不如直接标上"⚠ 计算异常"。诚实比好看重要。

**改法三：跟"躺着不动"比**

单看 0.001% 年化没概念，但如果并排：

> 本策略年化 0.001%，买入持有 2.34%

用户立刻明白"这策略还不如不折腾"。基线数据日志里就有，不用额外取。

## 四、我还想到的几个方向

### 4.1 让因子证明自己有用（高价值）

现在因子面板给了方向，但**回测里根本看不出因子起没起作用**。

办法是做对照实验：同一份代码，把因子门控改成永远放行，再跑一次回测，两组结果一比：

| | 有功能门控 | 无门控 | 差异 |
|---|---|---|---|
| 成交笔数 | 29 | 41 | -12 |
| 年化 | 0.001% | -0.12% | +0.12pt |

**这是唯一能回答"因子到底有没有用"的方法**，而且不用花大模型额度——改个常量重跑回测就行。

### 4.2 版本对比（中价值）

一个对话下生成了好几个版本，现在只能一个个点开。做个对比视图，把关键参数和结果并排放，一眼看出哪版更好。

### 4.3 生成质量趋势（中价值）

统计最近 N 次生成的验收通过率：

> 近 20 次：通过 12 次（60%）。上一版提示词通过率 35%。

这是判断"我们改提示词有没有用"的唯一客观依据，比拍脑袋靠谱。

### 4.4 失败样本库（中价值）

把没通过验收的策略归档，标注失败原因（没下单 / 零成交 / 标的不对 / 代码报错）。攒够了就能反哺：提示词针对高频问题加约束，验收门加新的检查规则。

### 4.5 代码静态检查（高价值、成本极低）

在回测跑之前先扫一遍代码，把明显有问题的拦下来：

| 看到什么 | 判定 |
|---|---|
| 只有打印日志，没有下单调用 | 直接拒 |
| 出现"POC""无法撮合""信号日志形式" | 自己都说是演示稿了 |
| 参数写死在代码里而不是声明成可调参数 | 提示 |
| 保证金比例明显不对（比如 1.2%） | 提示 |

25 个历史模板里 21 个零成交，至少一半能被这套规则提前拦住。每次省下 3–10 分钟的生成加回测时间。

### 4.6 因子时点还原（卡在对方那边）

这是**最根本的缺口**。

现在因子面板是"生成这一刻"的快照，写进代码就是一组常量。回测 2024 年的行情时，用的却是 2026 年的因子方向——严格讲这就是前视偏差。

要彻底解决，得让对方给因子编号，让回测运行时能按发布时间逐日读因子值。

**在此之前，所有"因子驱动策略"的回测结果都不能拿来证明因子有效。**

## 五、性能优化

### 5.1 先看清楚慢在哪

实测下来，瓶颈很明确：

```
首次数据库连接      2.09 秒   ← 就是这里慢
查询本身            0.05 秒   ← SQL 很快
第二次完整构建      0.72 秒   ← 预热后
```

**SQL 不是瓶颈，建连接才是。**

### 5.2 值得做的两处

**连接池预热（收益最大，5 行代码）**

服务刚启动时第一次请求要等 2 秒建连接。在启动时主动建一次，把等待挪到启动阶段，首个用户请求就从 2.6 秒降到 0.7 秒。

**因子面板加短缓存**

每次生成草稿都要重跑一遍新闻和因子查询，约 0.7 秒。同一时间窗内反复点"重新生成"其实结果几乎一样，加个 60 秒缓存就行。

注意：缓存要带上时间锚点，否则会拿到旧数据，破坏防前视。

### 5.3 不用优化的部分

SQL 0.05 秒、因子计算 0.06 秒、前端渲染 10 毫秒，全都在合理范围。

**别为了性能做过度设计。** 用户感知的 0.7 秒里，0.6 秒是不可避免的数据库往返，做完上面两项就接近这个架构的下限了。

## 六、优先级建议

| 优先级 | 做什么 | 工作量 | 依赖 |
|---|---|---|---|
| **P0** | 连接池预热 | 半小时 | 无 |
| **P0** | 代码静态检查 | 半天 | 无 |
| **P0** | 收益曲线 + 交易明细 | 1–2 天 | 无，日志里有数据 |
| **P1** | 策略概要四层结构 | 1–2 天 | 无 |
| **P1** | 指标分层 + 异常标记 | 半天 | 无 |
| **P1** | 提示词分段折叠 | 1 天 | 无 |
| **P2** | 因子贡献度归因 | 2 天 | 需联调 160055 |
| **P2** | 与买入持有对比 | 1 天 | 无 |
| **P3** | 版本对比 / 质量趋势 / 失败库 | 2–3 天 | 需数据积累 |
| **卡住** | 因子时点还原 | 2–4 周 | **需对方给因子编号** |

**建议顺序**：先做三个 P0（约两天），解决"看不出好坏"和"废策略浪费生成额度"这两个最痛的问题；再做 P1 三项，解决"看不懂"；P2 的归因分析等有稳定产出后再做。

## 七、必须说清楚的一件事

现在策略里的因子门控**其实一直放行**。

因为因子值是生成那一刻的快照，写进代码就是一组固定常量：净分 5.51，阈值 2.0，永远成立。

**所以现在这条策略，实质上就是一条纯双均线策略，跟因子没有关系。**

回测结果只能证明"代码能跑、链路是通的"，不能证明"因子有用"。

这个问题不解决，上面所有可视化都只是在让一个跟因子无关的策略看起来更专业。**所以哪怕卡在对方那边，4.6 也得一直推。**
