## 一、一页纸结论

1. **这条链路现在能"跑通"，但跑不出有用的东西。** 我们账号下 25 个策略模板、96 个会话，能正常登录、建会话、发需求、拿到代码、拿到"回测通过"。但 25 个模板里**只有 4 个真的产生了成交**（105 / 234 / 11 / 6 笔），其余 21 个全是 **0 成交**——包括我们现在 `.env` 里配的那个（67 个版本，回测 `passed=True`，`Total Orders = 0`）。它只打日志，从不下单。
2. **根本原因不是连不通，是"没人给它决策"。** 对端大模型只拿到我们一句话的需求 + 三个因子中文名，标的、模式、周期全靠它自己拍。它拍出来的东西要么标的选错（历史上在债券平台上生成过沪金期货策略），要么写成"只打信号日志、不下单"的 POC 演示稿。
3. **我们能改的只有两个地方，都在我们自己这边**：①发给它的那段文字（情报包）；②我们自己的验收门和展示。对端的提示词、模型、回测平台都改不了（提示词加密在 licence 里，且只认它认识的可交易品种）。
4. **因子要真正影响回测，需要对方给一个"因子编号"**。对端在跑 factor 模式时，会从策略代码里抠出 `factor_list` 里的字符串，原样塞给回测平台。我们没有任何已注册的编号，所以 factor 模式现在对我们等于不可用。这一条要谈。
5. **前端策略生成页必须改，但只改一个页面**：现在的「交易参数」里没有"标的"和"模式"，这正是问题源头；「指标与日志」把"回测通过"当成成功，但 0 成交也是 passed。加三个输入框、加一块因子面板、改一处判定文案即可，不用动路由和整体结构。

## 二、先纠正三个认知偏差（都很关键）

### 2.1 部署的不是 main 分支

你说的"实际我们部署了 main 分支"，与服务器实测不符。

| 证据 | 结果 |
|---|---|
| 部署机 `/opt/app/wangboquan/ksquant-PilotPolicy` 的 `git branch --show-current` | **`xy`** |
| 该目录 HEAD | `c2e4f58 repair crash`（2026-09-14） |
| `origin/xy` 上有、`origin/main` 上没有的提交 | **14 个**（兴业版本初始化 → 修 websocket） |
| 部署二进制 `strings \| grep xzgateway` | 命中 1 次；而 `origin/main` 全仓库搜 `xzgateway` **0 次** |
| 部署源码 `AiStrategyV2Task1.cpp` 字节数 | 191,998，等于 `origin/xy` 的同名文件（`origin/main` 是 153,991） |

**影响**：以后所有关于对端行为的判断，必须以 `xy` 分支为准，不能看 `main`。本地 `C:\project\dream\ksquant-PilotPolicy` 默认检出的是 main，看代码前要先 `git checkout xy`，否则会得出错误结论。**这件事要先和对方确认**：是他们有意部署 xy，还是以为部署的是 main。

### 2.2 文档里"模板 ID 不存在"这个 P0 阻断项已经不存在了

`策略生成系统-DreamStrategy-必要信息说明.md` §7.3 说 `.env` 里的 `DREAM_TEMPLATE_ID=6742a12d...` 在服务端查不到、会导致"未找到模板"。

实测：登录成功，账号下 25 个模板，这个 ID 赫然在列，名为「10Y国债期货高频ATR通道突破策略」，**67 个历史版本**，最新版本代码 7114 字符、`backtest_exit_code=0`、`passed=True`。所以**不需要做"自动建模板"（160050）**，那部分工作量可以省掉。

但要注意：这个模板**是对的模板、错的结果**——`Total Orders = 0`（下面细说）。

### 2.3 因子侧的数据是好的，但"能用的因子"只有 21 个

实测我方生产库：

| 指标 | 实测值 |
|---|---|
| 因子字典 | 381 个 |
| 因子事件流 `news_factor` | 64,717 条 |

| 模板名（节选） | 版本数 | 代码字符 | 退出码 | 结论 | **成交笔数** |
|---|---|---|---|---|---|
| 10Y国债期货高频ATR通道突破策略（**我们现在用的**） | 67 | 7,114 | 0 | passed | **0** |

| 7 个空模板 | 0 | 0 | -1 | — | — |

**两个结论**：

1. **"passed" 不代表策略有用。** 平台只要回测进程正常退出就算通过，源码里明确写着 `total_trade_count=0 is OK`。所以"回测通过"这个绿灯，正是我们要自己补的验收门要拆掉的东西。
2. **0 成交的成因是写出"POC/信号日志"式代码。** 我把我们那个 67 版模板的最新代码拉下来读了：它确实实现了双均线、止损止盈、仓位计算，逻辑没问题——但**全部动作只是 `self.Debug(...)` 打印**，一次下单接口都没调。代码注释里自己写着"以信号日志形式呈现交易指令"。模型被"POC/演示"这类词带偏了。

### 3.3 对端的硬性限制（我们的代码必须适配）

| 限制 | 数值 | 出处 |
|---|---|---|
| 单条消息长度 | ≤ **10,000 token**，超了直接报错 | `AiStrategyV2Task2.cpp:1691` |
| 单会话消息数 | ≤ **50 条**（报错文案误写成 20） | `AiStrategyV2Task2.cpp:1724` |
| **单用户同时只能跑一个生成** | 按 `user_id` 全局单飞；第二个请求直接被拒，推一条错误消息"其他AI生成任务正在执行中，请等待完成。" | `AiStrategyV2Task1.cpp:2219` |
| 自动重生次数 | **3 次**（校验/回测失败自动重来） | `AiStrategyV2Task.h:165` |
| 回测同时只能跑一个 | 全局一把锁，第二个回测直接返回 `-2` 拒绝 | `AiStrategyV2Task1.cpp:3021` |
| Token 预算换算 | **1 个汉字 = 1.5 token**（估算器 `Bitfin/DreamCore/TextTokenUtil.cpp`：ASCII 每字符 1、3 字节汉字每字 6，最后整体除 4），即 **10000 token ≈ 6666 个纯汉字**，纯英文则约 4 万字符 | 已按源码逐字核算 |

**这直接决定了我们的工程要求**：情报包要写死在本地上限内。按 1 汉字 = 1.5 token 计算，**安全预算建议 ≤4000 汉字（约 6000 token）**，给系统提示词和模型输出留出余量。这里必须留余量，不能贴着 6666 走——超出直接报错，没有截断兜底。

### 3.4 标的与因子：对端认什么、不认什么

我直接调了对端的 mock 行情服务（`http://10.253.50.112:20032`，注意**不是**文档写的 `127.0.0.1:20032`，55 机器上该端口不通）：

- 服务活着，有 `/api/v1/mock/` 系列接口，数据覆盖 2015-01-01 至 2026-05-20，`FCT_T_MAIN` 有 76 万条 1 分钟线。
- **它认识的可交易品种只有这几个**：`FCT_T_MAIN`、`FCT_TS_MAIN`、`FCT_TL_MAIN`、`FCT_AU_MAIN`、`IBK_G10Y_ACTV`、`IBK_CDB10_ACTV`、`100040`。
  - 注意：**没有 `FCT_TF_MAIN`（5 年期）**。
  - **没有我们任何一个因子名**——我拿 `RISK_APPETITE`、`SENTIMENT_GATE` 去查，返回 `unknown variety_code`。
- 它有一个 `/api/v1/mock/factors/list`，返回 367 个因子，但那是**股票技术因子文档**（资本利得突出量、残差反转、换手率分布…），**和我们的事件流因子完全不是一回事**，不能混。

**factor 模式到底怎么跑**（读源码得到的确切机制）：

1. 策略代码里写上 `factor_list = ['xxx']`；
2. 对端用正则从代码里把 `xxx` 抠出来，塞进回测请求的 `back_test_factor` 字段；
3. 回测平台按这个 `xxx` 去取因子数值序列，喂给策略的 `on_factors()`。

也就是说——**`factor_list` 里的字符串必须是"回测平台认识的因子编号"，不是我们自己起的名字**。我们没注册过任何编号，所以现在写什么都是白搭。这就是文档里说的"L2 通道需要对方配合"的实质内容。

## 四、我们要做成什么样（目标链路，一句话版）

> **我们出决策，它出代码，我们验收。**

```
我们（Sentiment）                                         对端（DreamStrategy）
────────────────────────────────────────────             ─────────────────────────────────
① 从 381 个因子里挑出「过关的」21 个
   （n≥20 且命中率跑赢基准）
        ↓
② 算当前信号：方向 + 强度 + 命中率 + 样本量
        ↓
③ 组装「情报包」：任务卡 + 因子面板 + 市场块 + 纪律
   （标的/模式/周期/开平骨架/风控 由我们写死）
        ↓
④ 发一条 ≤4000 汉字的消息  ──────────────────────────►  ⑤ 大模型把需求翻译成代码
        （原文，唯一合法输入通道）                          （不许自己选标的）
                                                                    ↓
                                                        ⑥ 提交回测平台跑
                                                                    ↓
⑦ 收到结果 ──────────────────────────────────────────  ⑦ 代码 + 回测日志 + 指标
        ↓
⑧ 【我们自己的验收门】
   · 有成交吗？（0 成交 → 不通过）
   · 下单类型和标的匹配吗？（禁止 XBOND 下单期货）
   · 指标能解析吗？
        ↓ 不通过就带着失败原因重发一轮（最多 2 轮）
⑨ 落库 + 展示
```

**和现在的差别只有三处**，但这三处决定了有没有用：

| | 现在 | 改后 |
|---|---|---|
| 标的 | 模型自己选（出过沪金事故） | 我们写死在任务卡里，且只从 7 个可交易品种里选 |
| 因子情报 | 只给 3 个中文名 | 给 8 个过关因子的完整面板：方向、信号分、命中率、基准、样本量、最近触发 |
| 验收 | 平台说 passed 就算成功（0 成交也算） | 0 成交一律不通过，自动带原因重生 |

## 五、具体怎么做（按顺序，四步）

### 第 1 步：因子信号面板内核（新增 1 个文件，约 1–2 天）

**做什么**：新建 `backend/strategy/signal_panel.py`，把"哪些因子能上桌、现在什么方向、有多可靠"算出来。

**输入**：`factor`（字典）、`news_factor`（事件流）、`factor_event_study`（命中率）三张表。
**输出**：最多 8 条因子记录，每条含：

```
中文名 / code / 大类 / 方向（多=收益率下行）/ 信号分（-1~+1）/ 命中率 / 多数类基准 / 样本量 n / 有效期 / 最近触发时间
```

**筛选规则（三条，硬性）**：
1. `sample_size ≥ 20`（样本太少统计不可信）；
2. `hit_rate > majority_base`（跑不赢"无脑猜"的因子不进面板）；
3. 按 `|信号分| × 命中率` 排序，取前 8；
4. 排除已知脏数据 `NEW_FACTOR`、`NEW_FACTOR_1`。

**信号分算法**：直接复用现有的 `/sapi/macro/signal` 逻辑（时间衰减 λ=0.1，约 7 天半衰期，阈值 ±0.3），不新造一套，避免两处口径打架。

**注意**：`/sapi/macro/signal` 现在**不支持 model 参数**，会把 doubao/deepseek/glm 三个模型的事件混在一起算。而三个模型的方向口径不一致。所以面板内核要自己查库、固定单一 model（建议 `glm`，因为它是当前在线模型；但 glm 只有 2026-07 之后的数据，历史回测要另说）。这一条要做成配置项。

### 第 2 步：情报包模板升级（改 2 个文件，约 1–2 天）

**做什么**：把现在的"五段式"提示词换成"情报包 v1"，版本号改为 `sentiment-intel-pack-v1`。

**改这两个文件**：
- `backend/strategy/sentiment_context.py`（现在只取 top3 正负向因子的中文名，见 266–303 行）
- `backend/integrations/dream/prompts/sentiment_strategy_chat_prompt_template.md`（29 行）

**新的情报包长这样**（预算 ≤4000 汉字）：

```
【策略任务卡】（强制，模型不得更改）
- 交易标的：FCT_TL_MAIN（30年国债期货）        ← 只从 7 个可交易品种里选
- 模式与周期：bar / 1d
- 回测区间：2024-01-01 ~ {锚点日}
- 开仓骨架：技术触发 + 情绪门控同向
- 平仓骨架：反向信号 / 止损1.5% / 止盈3.0% / 门控翻转
- 风控：单笔≤20%；门控冲突时空仓；下单接口必须与标的类型匹配
- 【硬性要求】必须真实下单，禁止只打日志；0 成交视为不合格

【因子信号面板】（仅列过关因子，≤8 个）
因子(中文/code)   方向  信号分  命中率(基准)  n   有效期  最近触发
货币政策周期      多    +0.72   0.63 (0.51)   47  5交易日 2026-10-27
...

【市场验证块】（锚点时点的客观行情）
国债曲线 1Y/5Y/10Y/30Y + 近5日 bp；信用利差与 20 日分位；中美利差；期货持仓多空比

【冲突与纪律】
信号冲突→降仓或空仓；禁止逐条新闻触发；禁止运行时访问外部数据源
```

**关键改动点**（现在的模板缺什么）：
1. **必须新增「交易标的」一项，并给出白名单**。现在模板第 11 行写的是"本轮不指定具体交易品种；请根据用户需求自行选择标的"——这一句就是沪金事故的直接来源。
2. **必须新增"禁止只打日志"的硬性要求**。实测 21/25 个模板 0 成交，其中至少我们那个是自己写着"以信号日志形式呈现"。
3. **因子从"3 个名字"升级成"带命中率的面板"**，让模型知道哪个因子值得当门控条件。

### 第 3 步：服务端健壮性 + 验收门（改 2 个文件，约 1–2 天）

**改 `backend/integrations/dream/service.py`**：

| 问题 | 现在 | 改成 |
|---|---|---|
| 对端报错不处理 | 只认 `content_type=4`（策略结果），收到 `content_type=5`（错误）会**傻等到 900 秒超时** | 收到 5 或 `strategy_generation_status=5` 立刻抛业务异常，30 秒内让用户看到原因 |
| 单飞冲突 | 没有处理，用户点两下会撞对端的"其他任务在跑" | 我方加进程内/数据库级队列锁，第二个请求排队并显示"排队中" |
| 0 成交也当通过 | `_backtest_is_complete` 只看 `exit_code ≥ 0` | 加验收门（下） |

**验收门（我方判定，与平台的 passed 无关）**：

| 检查项 | 通过标准 | 不通过 |
|---|---|---|
| 成交笔数 | `Total Orders > 0`（建议 ≥10 笔/年） | 带失败原因重生，最多 2 轮 |
| 下单接口匹配 | 期货标的不得用 `BusinessType.XBOND` | 重生 |
| 代码完整性 | 代码非空、可解析 | 重生 |
| 指标可解析 | Sharpe / 回撤等能读出 | 重生 |

## 八、卡在对方那边的事（要谈）

按重要性排序，前两条不解决，"因子真的驱动回测"这件事就没法验证。

1. **因子编号（factor_id）号段**。我们要把 21 个过关因子构造成日频数值序列推给金工因子平台，必须知道：编号怎么分配、我们能用哪个号段、回测平台认不认。**没有这个，factor 模式对我们完全不可用。**

   补充一条刚核实的依据：对端 API 手册里已经有"因子接口（FactorHandlerAPI）"章节，出现的 factor_id 形如 `1665916623805083648`、`1696824430582472704`、`1692121690417569792`——**是 19 位长整型**，且不同接口的号段不同。这不是我们自己能编的号，必须由对方分配。

2. **推送方式二选一**：
   - qfm 推送（推荐）：表 `qfm_factor_info` + `qfm_factor_data`，有 `publish_time` 字段，天然符合我们"按发布时间防未来函数"的纪律；
   - mock_factor HTTP：对端代码现成，我们实现一个 HTTP 服务即可，但更像测试通道。

3. **5 年期国债期货（FCT_TF_MAIN）为什么不在可交易品种里**。国债期货主力四个品种，现在只有 T / TS / TL 三个，缺 TF。是漏了还是数据没准备？

4. **回测平台 Bearer Token 我们账号配了没有**。我直连 `/qt` 返回 401，说明必须配置。现在只能通过页面上配好的人（admin）在用，我们的服务账号有没有配需要确认。
   - 另有一条要留意：这个令牌**只存在对端内存里，重启即失效**（`AiStrategyV2Task.h:328-336`，没有落库）。所以对端一重启，我们的生成就会全线失败在回测那一步，并且报的是"token not set"。这个运维事实必须告知对方。

5. **为什么部署的是 `xy` 分支而不是 main**（见 2.1）。

6. **生成结果和回测日志我们完整留存的合规要求**，以及策略代码的知识产权归属。

## 八·补、另一个高风险点：模型其实"看不见"标的校验工具

这一条是核查对端提示词时发现的，会直接影响我们"把标的写死"这个方案能否奏效，必须写进来。

对端的模型每轮都能调用工具，但**实际只给模型声明了 1 个工具**（`get_server_datetime`）。代码里另外实现了 `get_tradable_instrument_codes`（查可交易品种）和 `get_bond_basic_info`（查债券要素），但**没有声明给模型**，属于死代码。更关键的是，对端提示词原文要求：

> "策略直接采用用户提供的期货品种代码，**不要求、也不依赖品种校验工具**；无需调用品种查询/校验接口，不得因品种无法校验而中断、拒绝或延迟生成。"

**这意味着**：
- 好消息——**我们给的标的会被无条件采纳**，模型不会因为"查不到这个品种"而拒绝生成。把标的写死在任务卡里这条路是通的。
- 坏消息——**模型不会帮我们做任何标的合法性检查**。如果任务卡里写了一个对端不认识的代码（比如我实测不存在的 `FCT_TF_MAIN`，或者我们自己的因子名），模型会照样写进代码，回测那边才会崩，而且崩得很晚（要走完生成+回测全流程）。
- **对我们的要求**：白名单校验必须放在**我方发送之前**，不能指望对端。这正好也是需求文档 FR-3 要的，但要明确它是**唯一一道防线**，不是双保险。
