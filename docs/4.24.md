### 2.0 处理方式

处理方式都是一样：先查阅factor表中对应code字段，找到id字段，

然后去newsfactor里做剩下的操作，当然剩下的操作就根据不同策略不同了

```sql
CREATE TABLE `news_factor` (
  `news_id` bigint(20) unsigned NOT NULL,
  `factor_id` int(11) NOT NULL,
  `direction` text COLLATE utf8mb4_unicode_ci,
  `driver` text COLLATE utf8mb4_unicode_ci,
  `model` varchar(255) COLLATE utf8mb4_unicode_ci NOT NULL,
  `created_at` datetime DEFAULT CURRENT_TIMESTAMP,
  `pub_time` datetime DEFAULT NULL COMMENT '冗余新闻发布时间，用于时间过滤',
  PRIMARY KEY (`news_id`,`factor_id`,`model`),
  KEY `idx_news_factor_factor_id` (`factor_id`),
  KEY `idx_news_factor_news_id` (`news_id`),
  KEY `idx_news_factor_pub_time` (`pub_time`),
  CONSTRAINT `fk_news_factor_factor_id` FOREIGN KEY (`factor_id`) REFERENCES `factor` (`id`) ON DELETE CASCADE,
  CONSTRAINT `fk_news_factor_news_id` FOREIGN KEY (`news_id`) REFERENCES `news` (`id`) ON DELETE CASCADE
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='新闻及其对应因子表'
```

```sql
CREATE TABLE `factor` (
  `id` int(11) NOT NULL AUTO_INCREMENT,
  `code` varchar(255) COLLATE utf8mb4_unicode_ci DEFAULT NULL,
  `name` text COLLATE utf8mb4_unicode_ci,
  `category` text COLLATE utf8mb4_unicode_ci,
  `subcategory` text COLLATE utf8mb4_unicode_ci,
  `factor_type` text COLLATE utf8mb4_unicode_ci,
  PRIMARY KEY (`id`),
  UNIQUE KEY `code` (`code`),
  KEY `idx_factor_code` (`code`),
  KEY `idx_factor_category` (`category`(100)),
  KEY `idx_factor_subcategory` (`subcategory`(100))
) ENGINE=InnoDB AUTO_INCREMENT=165 DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='因子表'
```

比如对于“当日有央行公开市场操作、通胀 / 金融数据发布、政策表态等官方发布的...影响了...的宏观驱动事件，无驱动的纯量价异动直接过滤。(日频)”

就应该类似于这样的入参

```python
GET /api/macro/signal
  ?factor_code=OMO_VOLUME_SIGNAL
  &start_time=2025-01-01T00:00:00
  &end_time=2025-01-1T23:59:59
  &signal_type=presence        # directional | presence
```

那我们就根据 `pub_time` 确定时间范围，看是否有对应因子存在。

另外一种情况是：宏观趋势层，如央行货币政策周期明确（降息 / 宽松周期对应多头，加息 / 收紧周期对应空头），DR007 中枢持续下行 / 上行，MLF 利率调整方向与趋势。

这种入参 `&signal_type=directional`，那我们就需要根据 factor 表的 direction 字段，`positive` 代表这个因子对国债正向影响（利多），`neutral` 表示没有影响，`negative` 表示负面。

另外一个问题是对于多条新闻如何处理，这里我们采用简单加和叠加上时间衰减，pos 为 1，neu 为 0，negative 为 -1。离 end_time 越近时间权重越大，时间权重应该是个 0~1 的参数，具体数学形式我没有想好。



### 2.1 事件验证

事件验证：当日有央行公开市场操作、通胀 / 金融数据发布、政策表态等官方发布的...影响了...的宏观驱动事件，无驱动的纯量价异动直接过滤。(日频)


- `OMO_VOLUME_SIGNAL`（公开市场操作）这个已有
- `MAJOR_MACRO_DATA_RELEASE`（重要宏观数据发布）
- `POLICY_GUIDANCE`（政策表态）

### 2.2 宏观趋势层

宏观趋势层：央行货币政策周期明确（降息 / 宽松周期对应多头，加息 / 收紧周期对应空头），DR007 中枢持续下行 / 上行，MLF 利率调整方向与趋势。

- `MONETARY_POLICY_CYCLE`（货币政策周期）

### 2.3 事件过滤与平仓

事件过滤：无超预期宏观黑天鹅事件（如美联储超预期加息、地缘冲突）冲击，历史样本中有对应事件驱动的除外。

事件平仓：出现超预期宏观事件彻底改变当前宏观环境，立即平仓。

- `BLACK_SWAN_SHOCK`（黑天鹅冲击）这个已有
- `MACRO_REGIME_BREAK`（宏观环境突变）

### 2.4 宏观环境数据与相似度

宏观环境数据（货币政策空窗期、DR007 低波动、公开市场操作净额平稳、无重大宏观数据发布），同时要计算行情相似度。与过去 5 年历史全样本的等长窗口期数据匹配，筛选出相似度排名前 10 的历史匹配段。

- DR007 低波动 不处理
- 货币政策空窗期 直接靠MONETARY_POLICY_CYCLE这个分字段来判断，比如没有或者有但是是neutral
- `OMO_VOLUME_SIGNAL`（公开市场操作）这个已有
- `MAJOR_MACRO_DATA_RELEASE`（重要宏观数据发布）

### 2.5 宏观事件平仓

宏观事件平仓：出现央行政策调整、重大宏观数据发布等事件打破宏观平稳环境，立即平仓。（日频率）

- `POLICY_SHIFT_EVENT`（央行政策调整）
- `MAJOR_MACRO_DATA_RELEASE`（重要宏观数据发布）

### 2.6 宏观确认与反转平仓

宏观确认：货币政策周期与趋势方向一致，无反向政策信号，确认机构行为的宏观驱动逻辑成立。

宏观反转平仓：货币政策出现反向调整信号，彻底改变宏观驱动逻辑，立即全额平仓。

- `MONETARY_POLICY_CYCLE`（货币政策周期）
