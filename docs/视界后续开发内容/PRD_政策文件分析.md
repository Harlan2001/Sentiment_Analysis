# PRD：政策文件分析（工作流内）

> 面向产品、开发与业务方。
> 所属方向：业务覆盖主线（政策和法律法规）—— **改造版**

---

## 1. 原方案为什么作废

原计划是从公网采集政策文件原文入库。**实测 8 次尝试全部失败**：

| 尝试 | 结果 |
|---|---|
| 中国政府网搜索接口（多种参数组合） | `data` 恒为 null，**只返回统计分面**（文号/年份/部门计数），不返回文件列表 |
| 抓政策文件库 HTML 页面 | 页面可达（200），但列表是 **JS 异步渲染**，抓到的全是页脚链接 |
| TRS 系统分页接口（`index.json` 等） | 全部返回 404 页面，**接口路径未逆向出** |

**且**：现有 7,071 条政策新闻**全是媒体解读**（标题含《》的仅 131 条，正文含《》的 3,191 条经抽样确认**均为媒体评论**）。而平台**本来就能看政策新闻** —— 再做"政策新闻的另一种组织方式"，增量价值有限。

**结论**：从公网拿政策原文这条路走不通。

## 2. 改造方案：用户上传

**改为：用户上传政策文件 → 平台解析分析。**

**为什么这样合理**

| 维度 | 原方案 | 改造后 |
|---|---|---|
| 数据源 | 公网采集，**拿不到** | **用户提供**，问题消失 |
| 分析对象 | "新闻提到某政策" | **政策原文本身** |
| 合规性 | 爬取第三方，存疑 | ✅ 用户自己的文件，无风险 |
| 归属 | 原放市场板块，**不合适** | **工作流** —— 本就是"提交任务→系统处理"场景 |

## 3. 为什么放工作流

工作流（`/workflow`）**已有三个同类模块**，模式完全可复用：

| 现有模块 | 模式 |
|---|---|
| 研报分析（`research_report/`） | 上传 PDF → pymupdf 解析 → LLM 提取 → 导出 |
| 每日新闻总结（`news_summary/`） | 批量输入 → LLM 汇总 → 报告 |
| 报告生成（`report_generation/`） | 结构化生成 → 导出 |

**"政策文件分析"几乎是把研报解析的模式搬过来**，技术上不难。

## 4. 本期范围

### 做
- 工作流内新增「政策文件分析」入口
- 上传 PDF / Word / 文本 → 解析 → LLM 提取政策要点与影响方向
- 输出：政策要点摘要、涉及领域、对债市的**影响方向**（利多/利空/中性）、推理依据
- 复用研报解析的解析能力与导出能力

### 不做
- 从公网采集政策原文
- 人工维护的政策日历
- 政策文件的结构化数据库（不做全文检索库）
- 自动交易建议

## 5. 复用与新增

| 能力 | 来源 |
|---|---|
| 文件解析（PDF/Word） | **复用** `research_report/parser.py`（pymupdf） |
| LLM 提取与结构化 | **复用** `research_report/llm.py` 的模式 |
| 任务与状态管理 | **复用** `task_runs` / `task_events` |
| 导出 | **复用**研报导出能力 |
| 新增 | 政策专属的 prompt（提取要点 + 影响方向）、政策分析结果表 |

## 6. 页面设计

### 6.1 融合位置

**工作流内新增一个子模块**，与现有三个并列：

```
/workflow
├── 研报分析       ← 现有
├── 策略开发       ← 现有
├── 每日新闻总结   ← 现有
└── 政策文件分析   ← 新增
```

**为什么不放市场板块**：市场板块是"看数据"，工作流是"提交任务、系统处理"。政策文件分析属后者。

### 6.2 页面结构

**上传页**

```
┌─ 政策文件分析 ────────────────────────────┐
│ 上传政策文件（PDF / Word）                  │
│ ┌──────────────────────────────────────┐ │
│ │   拖拽文件到此，或点击选择               │ │
│ │   支持 PDF / DOCX / TXT，单文件 ≤ 20MB  │ │
│ └──────────────────────────────────────┘ │
│ 分析侧重  [债市影响] [要点提取] [全部]       │
│                              [开始分析]    │
└──────────────────────────────────────────┘
```

**分析结果页**

```
┌─ 《关于×××的通知》────────── 分析完成 ─────┐
│ 政策要点                                    │
│  · 要点一 …                                 │
│  · 要点二 …                                 │
│                                            │
│ 涉及领域   [货币政策] [财政政策]              │
│                                            │
│ 对债市影响  偏多                            │
│ 依据：文件提出……，预计…（引用原文片段）        │
│                                            │
│                        [导出分析报告]        │
└────────────────────────────────────────────┘
```

### 6.3 展示纪律

- **明确这是"对上传文件的 AI 解读"，不是官方解读**
- 影响方向必须**引用原文片段**作为依据，不能凭空判断
- 标注分析所用模型与时间

## 7. 现有 `/policy` 页的处置

**撤下该页**（从导航移除）。

理由：它的能力（政策新闻按因子聚合）与新方向重复，且底层数据是媒体解读，增量价值有限。

**保留**：现有 `policy_event` 表与后端接口**不删**（数据保留，便于将来若拿到文件源再启用）；仅从前端导航移除。

## 8. 怎么融合到现有产品

| 集成点 | 做法 | 是否动现有代码 |
|---|---|---|
| 前端 | 工作流新增子模块入口 | 是（工作流首页加一项，模式照抄现有三项） |
| 前端 | **移除 `/policy` 导航项** | 是（导航配置删一行） |
| 后端 | 新增政策分析路由与服务 | 否（纯新增） |
| 解析能力 | **复用** `research_report/parser.py` | 否（复用） |
| LLM 能力 | **复用** `common/llm_call.py` | 否（复用） |
| 数据表 | 新增政策分析结果表；**`policy_event` 保留不动** | 否 |
| Agent / MCP | 新增接口后需**重新导出** `backend/agent/data/openapi.json` | 需重新导出 |

## 9. 验收标准

- [ ] 能上传 PDF / Word / TXT 并成功解析
- [ ] 输出政策要点、涉及领域、影响方向与原文依据
- [ ] 影响方向**必须附原文片段**，无依据不输出方向
- [ ] 分析失败有明确错误提示
- [ ] 文件大小与类型限制生效
- [ ] 工作流现有三个模块**无回归**
- [ ] `/policy` 已从导航移除，但后端接口与数据保留
- [ ] 重新导出 openapi.json

## 10. 风险

| 风险 | 应对 |
|---|---|
| LLM 对政策影响判断失真 | **必须引用原文片段**作为依据；标注"AI 解读，非官方" |
| 上传文件含敏感信息 | 复用研报上传的既有处理方式；不额外留存原始文件 |
| 解析失败（扫描件/图片 PDF） | 明确提示"未识别到文本"，不静默失败 |
| 与"研报分析"功能重叠 | 定位区分：研报=券商观点，政策=官方文件；prompt 与输出结构不同 |
