# PRD：回测仿真（因子事件研究）

> 本文档面向产品、开发与业务方，说明这个模块为什么做、怎么做、前端如何设计。
> 所属方向：可信度主线（让分析结论可被验证）

---

## 1. 背景与问题

平台的核心分析链路是：**新闻 → 因子 → 信号 → 预测**。这条链路产出大量判断，但**没有任何事后验证机制**。

用户看到的是"某因子今天发表了利多判断"，但无法回答：**这个因子历史上一贯准吗？**

这是平台可信度的根本缺口——和《PRD：预测诊断》要解决的问题同类，只是验证的对象不同（预测诊断验证"报告"，本模块验证"因子"）。

## 2. 一个关键的方案选择

原始需求希望做"信号回测"——统计每个因子的**信号胜率**。我们实测后发现**这条路走不通**：

现有 directional（方向性）信号日志的真实情况：

| 指标 | 实测值 |
|---|---|
| 总行数 | 47 行 |
| 覆盖因子 | 19 个 |
| **不同时间窗** | **仅 8 个** |
| 其中只有 1 个样本的因子 | **9 个** |

更严重的是那 8 个时间窗**大量重叠**——实际发出时间集中在 2026-09-23 / 24 / 29 三天内：

```
窗口[2026-09-01 ~ 09-22] 发出=09-23
窗口[2026-09-01 ~ 09-23] 发出=09-23   ← 与上一条高度重叠
窗口[2026-08-23 ~ 09-23] 发出=09-23   ← 与上一条高度重叠
窗口[2026-09-01 ~ 09-24] 发出=09-24
窗口[2026-09-17 ~ 09-24] 发出=09-24   ← 回头重算同一段时间
```

**这意味着**：47 行不等于 47 个独立样本，真实独立观测大约只有 **8–10 个**。而且 directional 信号是**按查询窗口实时计算**的，历史窗口无法补算独立样本（补算等于用今天的因子库回算过去，即"未来函数"）。

**结论：用信号做回测，每格样本 1–2 条，做出来的胜率反而会误导业务。**

### 替代方案：改为"因子事件研究"

改用 **`news_factor` 表**（因子与新闻的关联记录），做**事件研究**：

> 「某因子出现 → 之后 T+1 / T+5 / T+20 的 10Y 国债收益率变动」

实测该表有 **64,447 行、跨 2021-09 ~ 2026-10、覆盖 381 个因子**，其中 **108 个因子样本数 ≥ 100**（如 `RISK_APPETITE` 3,941 条、`GDP_GROWTH_EXPECTATION` 1,917 条）。

**样本量比信号大三个数量级，统计上真实可用。**

## 3. 这个模块解决什么

给因子一个**历史表现档案**：这个因子过去触发过多少次、之后市场通常怎么走、准不准。

## 4. 本期范围

### 做
- 按因子统计事件研究结果：**样本数、方向命中率、平均变动、中位数**（单位 bp），持有期 T+1 / T+5 / T+20
- 因子详情页展示该因子的历史表现
- **样本 < 20 显式标注"样本不足"**

### 不做
- 收益类、回撤类指标（债券方向信号不适用收益/回撤口径）
- 概率校准
- **多因子横向对比排名** —— 见下节说明
- qlib / vectorbt / QuantStats 等回测框架（用 SQL + pandas 足够）

### 为什么不控"因子排行榜"

原需求希望做"多因子横向对比、按类别聚合"。**本模块明确不做排名**，原因：

**利率债的因子信号是同源的**——它们都来自同一批新闻文本的 LLM 判断。因子之间**不具备统计独立性**。对同源信号做横向胜率排名，**很容易得出"某因子更准"的伪结论**，而真实原因可能只是它背后的新闻数量更多、或集中在某个特定市场环境。

**替代做法**：本模块只做**单一因子的时间序列稳定性展示**（这个因子在不同时间段表现是否一致），不做跨因子排名。

## 5. 数据设计

新增表存回测结果，字段：因子代码、持有期、样本数、方向命中率、平均变动（bp）、中位数（bp）、计算时间。

**幂等要求**：按 `(因子, 持有期, 计算批次)` 去重，重复计算不产生重复事实记录。

**性能考虑**：`news_factor` 有 6.4 万行，全量回测需按日期与因子建索引，避免全表扫描。结果**定期批量计算并落库**，不要在页面请求时实时计算。

## 6. 两条必须遵守的纪律

### 纪律一：严格防未来函数

事件研究的时间对齐必须严格：

```
信号日 t  →  只用 t 及之前的数据判断
             收益从 t+1 开始算，到 t+N 结束
```

**这是本模块最容易出错的地方**，也是最容易让结果"看起来很好"的地方。必须写测试覆盖。

### 纪律二：按交易日对齐，不按自然日

**不引入节假日依赖**。实测 `yield_data` 的日期集合**就是权威的中债估值发布日历**——其中 50 个"周末日期"恰好是中国的调休补班日（2020-04-26 与 2020-05-09 成对、2020-09-27 与 2020-10-10 成对、2021-02-07 与 2021-02-20 成对）。

所以：`SELECT DISTINCT date FROM yield_data` 即可得到交易日序列，**按交易日序号推进 T+N，不按自然日**。

> 若按自然日推进，周末与节假日会造成"T+1 实际是 3 天后"，结果系统性失真。

## 7. 页面设计

### 7.1 融合位置

**推荐方案：在现有因子详情页新增区块。**

现有路由已有 `/factor/:factorId`（因子详情页）。本模块**在页面下方新增一个"历史表现"区块**，不动现有内容（因子定义、关联新闻等）。

```
/factor/:factorId
├── 因子定义（现有）
├── 关联新闻（现有）
└── [历史表现]   ← 本模块新增：事件研究结果
```

**为什么不新建独立页面**：因子表现是**因子的一个属性**，用户是在看某个因子时想知道"它准不准"，独立页面会造成来回跳转。

> 详细归位依据见《前端信息架构.md》。

**备选**：因子列表页（`/factors`）可增加一列信号质量标签（高/中/低/样本不足），但**本期不做**（需先积累数据）。

### 7.2 历史表现区块设计

```
历史表现                    计算于 2026-10-21
┌────────────────────────────────────────────┐
│ 基于 1,917 次历史事件（2022-01 ~ 2026-10）    │
│                                            │
│ 持有期    样本    方向命中率   平均变动   中位数 │
│ T+1     1,891     54.2%      −0.8bp    −0.5bp│
│ T+5     1,845     58.7%      −2.1bp    −1.8bp│
│ T+20    1,702     61.3%      −5.4bp    −4.9bp│
│                                            │
│ ⚠ 命中率对照：多数类基准 62.1%                  │
│                                            │
│ ▁▂▃▅▂▁  分年度命中率（看稳定性）               │
└────────────────────────────────────────────┘
```

**关键展示要求**

1. **必须显示对照基准**。与《PRD：预测诊断》同一个道理——方向命中率的正确对照线是**多数类基准**（那段时间市场多数时候往哪走），不是 50%。**没有基准的命中率会被严重误读。**

2. **样本数常驻**。用户需要知道这个结论有多可信。

3. **样本 < 20 时显示"样本不足"**，不展示命中率数字。避免用小样本得出误导性结论。

4. **分年度命中率**（走势条）。这是本模块**最有价值的部分**——它回答"这个因子是一贯有效，还是只在某个市场环境下有效"。一个因子总命中率 60% 但分年度从 80% 掉到 30%，比总命中率 55% 但年年稳定 55% 要可疑得多。

### 7.3 与因子列表页的关系（本期不做）

后续可在 `/factors` 列表页为每个因子加一列**质量标签**：

| 标签 | 判据 |
|---|---|
| 高 | 命中率显著高于基准，且样本充足（≥ 100） |
| 中 | 命中率与基准无显著差异 |
| 低 | 命中率显著低于基准 |
| 样本不足 | 样本 < 20 |

**本期先不做**：需积累数据、且需先确认基准口径。等本模块产出结果、观察一段时间后再加。

## 9. 验收标准

- [ ] 能对因子计算 T+1 / T+5 / T+20 的事件研究结果
- [ ] 输出样本数、方向命中率、平均变动、中位数
- [ ] **防未来函数验证通过**（写测试：信号日只用当日及之前数据，收益从 t+1 起）
- [ ] **按交易日对齐验证通过**（跨周末/节假日的 T+N 正确）
- [ ] 样本 < 20 的因子显示"样本不足"，不展示命中率
- [ ] 页面显示多数类基准对照
- [ ] 分年度命中率可展示
- [ ] 现有因子详情页**行为无回归**
- [ ] 未修改任何信号/因子计算逻辑
- [ ] 重新导出 openapi.json，Agent/MCP 能调用新接口

## 10. 风险与注意

| 风险 | 说明 | 应对 |
|---|---|---|
| **未来函数** | 最常见也最隐蔽的错误，会让结果虚假变好 | 写**专门测试**覆盖；代码评审重点检查 |
| 自然日 vs 交易日 | 跨周末导致 T+1 实际是 3 天后，结果失真 | 按交易日序号推进；用 `yield_data` 日期集合 |
| 因子同源性 | 因子间不独立，横向排名会得出伪结论 | **明确不做排名**，只做单因子时间序列稳定性 |
| **因子库本身不可信** | 实测发现中文向量模型用错，因子去重闸门失效——**同名同义因子会重复入库**（"通胀预期"比库里已有的"通胀预期"只得 0.664，低于 0.7 阈值） | ⚠ **这意味着"同一因子"的历史事件可能被拆散在两个重复因子里，导致样本虚低、结果失真**。见下节 |
| 全表扫描性能 | `news_factor` 6.4 万行 | 建索引；结果批量计算落库，不在请求时实时算 |
| 小样本误导 | 因子样本少时命中率波动极大 | 样本 < 20 显示"样本不足" |

## 11. 一个必须先说明的依赖问题

实测确认**中文向量模型用错了**（用了英文模型 `all-MiniLM-L6-v2`，中文模型 `text2vec-base-chinese` 已备好却未启用），导致**因子去重闸门失效**——语义重复的因子会被当作新因子入库。这解释了因子库膨胀到 381 个、其中 320 个是概念型。

**对本模块的直接影响**：如果一个因子在库里存在**同义重复项**，那么它的事件会**被拆散**到两个（或多个）因子记录里，导致**每个的样本数都虚低、方向统计也可能不一致**。

**处理方式**：该问题已记录在《开发方向总纲》的存量问题清单，**本期不修**。本模块先按当前因子库计算，但**需注意两点**：

1. 统计时若发现某因子的样本数明显偏低（与它在因子库中的活跃度不符），该结果需谨慎解读
2. 因子库修复后（换中文模型 + 重建索引 + 重新标定阈值），**本模块结果需重算**

这不是本模块的缺陷，而是它依赖的上游数据质量问题——**如实记录，便于后续追溯**。
