# 债券市场智能分析平台 — 产品主线与完善建议

## 一、产品定位

**中国国债市场舆情→因子→信号→策略→决策的一站式智能分析平台。**

目标用户：债券交易员、策略分析师、金工研究员。核心价值是将碎片化的新闻舆情转化为可执行的结构化策略信号。

**产品化方向**：当前项目已完成从单体分析工具向多租户 SaaS 产品的架构演进，具备组织管理（公司/部门/角色）、用量计量（Token 消耗追踪）、用户行为分析、运营监控看板等产品化基础设施，后续将以机构订阅制 SaaS 形态对外交付。

## 二、核心逻辑链路（故事线）

│ ① 数据采集│ ② 智能分析│ ③ 因子信号│ ④ 策略生成│ ⑤ 变动追踪│ ⑥ 报告分发│ ⑦ 监控运营│ ⑧ 研报分析 │
│  Data    │ Analysis │ Signals  │ Strategy │ Change   │ Report   │Monitor   │Research   │
├──────────┼──────────┼──────────┼──────────┼──────────┼──────────┼──────────┼───────────┤

### 阶段 ①：数据采集 — "市场发生了什么"

| 数据源 | 载体 | 频率 |
|--------|------|------|
| 财经新闻（华尔街见闻、第一财经等） | `news` + `news_content_blocks` | 持续爬取 |
| 国债收益率曲线 | `yield_data` | 每日更新 |
| 债券标的池 | 外部 API / 本地快照 | 按需同步 |
| 策略库（量化策略 + 交易策略） | 外部 API / 本地快照 | 按需同步 |

### 阶段 ②：智能分析 — "这些事件意味着什么"

每条新闻经过 LLM（Doubao/DeepSeek/Qwen）分析，输出的结构化 JSON 包含：

- **direction**：对国债的利多/利空/中性方向
- **horizon**：短期（1周-1月）/ 中期（1-6月）/ 长期（6月+）
- **reason**：逻辑推导链（触发事件 → 中间变量 → 利率方向）
- **factors**：关联的因子列表（优先复用已有因子，自动发现新因子）

同时，新闻文本经 `sentence-transformers` 编码为 384 维向量，存入 FAISS 索引 + MySQL，支持相似新闻检索。

关键表：`analysis`（新闻→情感方向）、`news_factor`（新闻→因子关联）、`news_vectors`（向量存储）

### 阶段 ③：因子信号 — "哪些因子正在被触发"

基于阶段 ② 的因子关联结果，提供两类量化信号：

- **Presence 信号**（0/1）：指定时间窗口内某因子是否有相关新闻
- **Directional 信号**（-1/0/1）：加权方向信号，使用指数时间衰减（近期的新闻权重更高），输出置信度

关键表：`factor`（因子目录，~290 个）、`macro_signal_request_log`（API 调用审计日志）

### 阶段 ④：策略生成 — "现在应该怎么做"

三条并行的策略输出线：

1. **交易策略推送**（`StrategyPushService`，每 30 分钟）：基于滚动窗口内的新闻分析理由，LLM 生成 120-220 字的中文交易建议，通过 SSE 实时推送到前端
2. **组合策略分析**（`PortfolioStrategyService`，按需触发）：LLM 输出组合久期区间、最低评级要求、品种/类型分布权重
3. **AI 标的推荐**（`strategy_recommendation.py`，每日）：将新闻分析 + 债券标的池 + 策略库输入 LLM，输出 1-5 条标的-策略匹配推荐

关键表：`strategy_push_history`、`portfolio_strategy_analysis_cache`、`ai_strategy_recommendation`

### 阶段 ⑤：策略变动对比 — "发生了什么变化"

- 每小时生成策略快照（24h 滚动窗口）存入 `strategy_change_snapshot`
- 可比对任意两个版本的差异：哪些标的新增/移除/评级变化、哪些策略新增/移除/优先级变化

### 阶段 ⑥：报告生成与分发 — "把结论传递出去"

- **每日预测报告**（`generate_report.py`）：LLM 综合 3 日新闻 + 收益率曲线 + 市场摘要 → 结构化 JSON（市场概览、技术分析、因子分析、日/周/月预测、情景分析、策略建议、风险提示）
- **PDF 生成**：Jinja2 模板 + Playwright 渲染 → PDF
- **多渠道推送**：飞书群机器人（PDF 附件 + 文字摘要）、微信公众号（PDF 转 PNG → 图文编辑器）

### 阶段 ⑦：监控运营 — "系统在发生什么"

产品化运营基础设施，确保平台健康运行并量化用户价值：

- **业务看板**（`DashboardPage.tsx`）：系统健康（MySQL 延迟）、数据管道监控（新闻→分析→因子→向量→收益率→预测，6 个模块全覆盖）、历史快照留存
- **用户行为分析**（`BehaviorPanel.tsx`）：全量页面浏览追踪（路由、进入/离开时间、停留时长、退出类型）、交互事件埋点（30+ 操作类型，含新闻点击、报告查看、图表交互等）、24h 活跃热力图、7 天趋势、页面排名
- **用户画像系统**（`UserProfilePanel.tsx`）：自动构建用户行为画像（活跃天数、高频操作、时段偏好、页面偏好），高价值用户识别、流失风险评估，支持 2-3 人画像对比（雷达图可视化）
- **用量计量**（`TokenOverviewPanel.tsx`）：每次 LLM 调用全量追踪（用户、模型、来源、prompt/completion tokens、延迟、成功/失败），按日/月/模型/来源/用户多维聚合，为 SaaS 订阅计费提供数据基础
- **组织管理**：公司→部门→角色（admin/manager/user）三级权限模型，部门级使用概览（经理角色），个人使用仪表盘（每位用户可查看自己的用量与行为统计）
- **底层机制**：前端全局行为追踪 Hook（`useBehaviorTracker.ts`），5 分钟空闲超时检测，批量事件上报；后端读写缓存模式（1 分钟 TTL）

关键表：`dashboard_metric_cache`、`dashboard_snapshot`、`user_session`、`user_page_view`、`user_behavior_profile`、`llm_usage_log`

### 阶段 ⑧：研报分析 — "机构怎么看待市场"

除新闻舆情外，引入专业机构研报作为另一维度信息源，实现多源交叉验证：

- **研报入库**（`research_hash.py`）：PDF 研报 SHA256 去重 + 规范化命名，按年月归档
- **关键结论提取**：LLM 从研报中提取机构对利率方向、关键因子的判断，与新闻舆情信号对比验证
- **机构观点聚合**：按机构/分析师/时间维度聚合观点，追踪机构预测准确率
- **多源交叉验证**：新闻舆情信号 ↔ 机构研报结论 ↔ 宏观指标数据，三方验证后输出更高置信度的策略信号

## 四、当前碎片化问题诊断

### 问题 1：页面之间缺少"超链接"式导航

用户在新闻页面看到某条新闻关联了因子 X，但无法一键跳转到因子 X 的详情页。同样，预测报告中的结论无法追溯到源新闻。

### 问题 2：数据流完整但用户不可见

技术层面 `news → analysis → news_factor → macro_signal → strategy` 链路完整，但前端没有一处展示这个完整链路。

### 问题 3：看板业务指标不足（部分解决）

看板（`/dashboard`）已具备系统监控、行为分析、用量计量等运营能力，但仍缺少**市场维度的业务指标**（当前市场情绪方向、活跃因子 Top5、最新策略建议摘要、预测准确率）。当前看板的"业务总览"标签页定位为运维层面，尚未融入分析决策链路。

### 问题 4：Agent 工具能力有待扩展（部分解决）

Agent 已接入 8 个工具函数（`search_news`、`compute_macro_signal`、`get_yield_curve` 等），可查询基础数据。但仍缺少对策略推荐、预测报告、研报分析结果的高级查询能力，无法回答"今天的策略建议是什么"或"机构研报对利率怎么看"。

### 问题 5：报告缺乏交互性

预测报告是静态文本，前端无法点击某个预测结论查看其依据。

### 问题 6：变动对比缺少事件归因

策略变动展示了"什么变了"，但没有展示"为什么变"——即哪些新闻事件的流入/流出导致了策略变化。

### 问题 7：研报与主链路割裂

研报分析模块（规划中）尚在建设，当前与新闻舆情→因子→策略主链路无数据联动。研报中的机构观点无法与新闻舆情信号做交叉验证，也无法纳入策略生成和预测报告的数据源。

### 问题 8：多租户产品化配套不足

公司/部门/角色权限模型已建立，Token 计量已实现，但缺少订阅管理（套餐定义、用量配额、超量策略）、许可证管理（有效期、用户数上限）和租户级配置隔离。

## 五、技术上严格可行的完善方案

以下方案按优先级排列，均基于现有代码架构，**无需重构核心逻辑**。

### P0（最高优先级）：建立链路导航与数据联动

#### 1. 新闻详情页增加"完整链路面板"

**现状**：[NewsDetail.tsx](frontend/src/components/Pages/NewsDetail.tsx) 展示新闻内容、情感方向、因子标签、相似新闻、收益率图表，但各部分独立排列。

**方案**：在新闻详情页顶部增加一个"分析链路"横向步骤条：

```
[新闻事件] → [情感: 利多] → [因子: LIQUIDITY_TIGHTENING ×3] → [信号: directional=-1] → [相关策略: 2条]
```

每个步骤可点击展开详情。后端已有所有数据，前端只需组合展示。

**涉及文件**：
- 前端：`NewsDetail.tsx`（新增链路面板组件）
- 后端：已有 API `/sapi/news/{id}` 返回分析+因子，可扩展返回关联策略

#### 2. 看板增加"市场脉搏"业务指标行

**现状**：`DashboardPage.tsx` 已具备系统监控、行为分析、用量计量等完整运营面板能力，但缺少市场分析决策维度的实时业务指标。

**方案**：在看板顶部或"系统监控"标签页中新增"市场脉搏"行：

**方案**：在看板顶部新增"市场脉搏"行：
- 当前市场情绪方向（基于近 24h 新闻方向占比）
- 最活跃因子 Top5（基于近 24h news_factor 计数）
- 最新策略建议摘要（最新一条 strategy_push_history）
- 最新报告核心结论（最新 forecast_report 的报告摘要字段）

这些数据后端几乎都能从现有 API 拼凑，最简方案是在 `/sapi/dashboard/core` 中追加这些聚合字段。

**涉及文件**：
- 前端：`DashboardPage.tsx`、新增 `MarketPulse.tsx`
- 后端：`dashboard_service.py`（扩展 core 接口返回）

#### 3. 因子页增加活跃度与信号联动

**现状**：`FactorPage.tsx` 仅展示因子目录。

**方案**：
- 每个因子卡片增加"近 7 天触发次数"和"当前 directional 信号值"
- 点击因子进入详情时，展示该因子的触发新闻时间线 + 信号历史曲线
- 后端：因子列表 API 增加近 N 天统计字段；复用 `macro_signal.py` 的 `get_macro_signal()` 计算实时信号

**涉及文件**：
- 前端：`FactorPage.tsx`、`FactorCard.tsx`、新增 `FactorDetailPanel.tsx`
- 后端：`factors.py` router（扩展 `/sapi/factors` 返回字段）

### P1（高优先级）：建立预测报告的可追溯性

#### 4. 预测报告增加"数据来源"标注

**现状**：预测报告是 LLM 生成的纯文本，无法追溯。

**方案**：
- 在 `generate_report.py` 的 prompt 中要求 LLM 对每个关键结论标注引用的新闻编号（新闻 1、新闻 2...），生成 JSON 中增加 `source_news_ids` 字段
- 前端 `PredictionPage.tsx` 展示报告时，将标注的新闻编号渲染为可点击链接，跳转到对应新闻详情

**涉及文件**：
- 后端：`generate_report.py`（修改 prompt + JSON schema）
- 前端：`PredictionPage.tsx`（解析 source 引用并渲染链接）

#### 5. 策略变动增加事件归因

**现状**：`ChangePage.tsx` 对比两个快照，展示标的/策略的增删改。

**方案**：
- 在对比结果中增加"新闻变动"面板：展示两个快照窗口之间新增/移除的新闻标题列表
- 后端 `change_service.py` 的 `compute_diff()` 函数中，已有 `news_added_count` / `news_removed_count` 统计，扩展为返回具体的新闻 ID 和标题列表

**涉及文件**：
- 后端：`change_service.py`（扩展 `compute_diff()` 返回新闻变动明细）
- 前端：`ChangePage.tsx`（新增新闻变动面板）

### P2（中优先级）：Agent 工具扩展 + 研报集成

#### 6. Agent 工具能力升级

**现状**：Agent 已实现 8 个工具函数（`search_news`、`get_news_by_date`、`get_news_detail`、`find_similar_news`、`list_factors`、`get_news_by_factor`、`compute_macro_signal`、`get_yield_curve`），支持 SSE 流式 + 工具调用进度可视化。

**方案**：扩展工具集，新增以下查询能力：
- `query_latest_strategy()`：获取最新策略推送摘要
- `query_prediction(date)`：查询指定日期的预测报告
- `query_research_report(date)`：查询研报分析结论（研报模块完成后）
- `query_user_usage()`：查询当前用户的 Token 用量

**涉及文件**：
- 后端：`agent/tools.py`（新增工具定义）、`agent/tool_executor.py`（新增执行逻辑）
- 前端：Agent 聊天界面已支持工具调用进度展示，无需大改

#### 7. 研报分析模块 MVP

**现状**：`research_hash.py` 已实现 PDF 哈希去重入库基础工具，研报分析功能处于规划阶段。

**方案**：
- 后端新增研报解析 pipeline：PDF → 文本提取 → LLM 结构化（机构、分析师、方向判断、关键因子、置信度）
- 新增 `/sapi/research` API：研报列表、详情、机构观点聚合、预测准确率追踪
- 前端新增研报分析页面，展示机构观点与新闻舆情信号的对比矩阵

**涉及文件**：

## 七、技术约束与注意事项

1. **LLM 调用成本**：看板"市场脉搏"中的实时聚合数据应使用 SQL 统计而非 LLM 调用，避免每次刷新产生成本。Token 计量系统（`llm_usage_log`）已记录每次调用的详细消耗，可基于此数据做成本优化分析。
2. **SSE 连接的复用**：策略推送已使用 SSE，Agent 对话也使用 SSE 流式。若增加更多实时推送（如因子信号更新），应复用同一 SSE 通道而非新建连接。
3. **SaaS 离线模式兼容**：部分功能依赖外部 API（策略库、债券标的），在 `USE_LOCAL_SNAPSHOT=true` 模式下使用本地快照数据。新增功能应同步兼容两种模式。
4. **数据库查询优化**：因子活跃度统计需要按时间窗口聚合 `news_factor` 表，建议对 `pub_time` 字段增加索引（已有 `idx_news_factor_pub_time`）。行为分析查询涉及 `user_page_view`、`user_session` 表的聚合，注意大时间窗口下的查询性能。
5. **前端性能**：避免在列表页对每条数据独立请求详情，应通过后端聚合接口批量返回。行为追踪采用批量上报机制（`behaviorLogger.ts`），避免高频单次请求。
6. **多租户数据隔离**：Token 计量和用户行为数据已按 `username`/`user_id` 区分，后续订阅管理需确保套餐配额查询与租户 ID 绑定，避免跨租户数据泄露。
7. **PDF 研报处理**：机构研报 PDF 体积较大（通常 10-50MB），解析 pipeline 应异步处理（任务队列），避免阻塞 Web 请求。PDF 文本提取的准确率直接影响下游 LLM 分析质量，需对不同排版格式的研报做好适配。
8. **行为数据保留**：用户行为日志（`user_page_view`）写入量大（每次页面访问一条），需设置合理的保留周期（已配置 `BEHAVIOR_LOG_RETENTION_DAYS`），定期清理过期数据。
