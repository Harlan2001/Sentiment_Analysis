## 0. 一页纸结论

1. **它是金仕达（ksquant）FICC 投研平台里的一个"AI 策略生成助手"**：你用大白话提需求，大模型生成一段 Python 策略代码，平台自动拿去回测，把代码和回测结果一起存下来。当前部署版本**定位是研究/辅助工具，不能实盘下单**。
2. **现役只有 V2 模式（聊天生成式）**。老的 V1 模式（内置脚本自动执行、可实盘）在编译时已被整体剔除，服务也处于关闭状态。
3. **它的输入只有一个：聊天文本**。没有任何"舆情接口""因子接口"的注入位——我们的情报只能组织在发给它的文字里（这是官方支持的正道）；因子数值若想在回测运行时被策略读取，需要走金仕达因子平台（第二条通道，需对方配合）。
4. **它现在几乎没人用，而且生成质量实测较差**：库里 9 个模板、7 个会话，全是同一账号 8–9 月的测试；最典型的样本是在"债券策略平台"上生成了一个**沪金期货双均线**策略，230 个交易日 **0 成交**，下单接口还选错了类型。这恰好说明：**让大模型自己选标的、拍参数是不可靠的，标的与交易骨架必须由我们的舆情/因子情报来给定。**
5. **我们当前的对接配置有一个硬伤**：`.env` 里配置的模板 ID 在服务器上**不存在**，而"建会话/发消息"服务端强制校验模板归属——不修复的话，我们页面上点"确认生成"会直接收到"未找到模板"错误。详见 §7。
6. **好消息**：协议层我们已经完全打通（WebSocket + Protobuf，登录、建会话、订阅、发提示词、收结果、轮询回测均已实现并与线上版本核对一致），差的不是"能不能连"，而是**配置修复、错误处理、以及喂给它的情报质量**。

## 2. 一次策略生成的完整过程

```
我们的后端                              DreamStrategy 服务（10.242.184.55）
   │  ① 拉门户配置 config.json（WS地址+公钥令牌）
   │───────────────────────────────►  门户 nginx（10.253.50.112:20026 → :20231）
   │  ② WebSocket 连接 + 登录（session_key+令牌）
   │  ③ 在某"模板"下创建聊天会话
   │  ④ 订阅该会话的消息推送
   │  ⑤ 发送一条消息 content（我们组织好的情报+需求，纯文本 ≤10000 token）
   │                                   │
   │                                   ├─ ⑥ 取历史消息，拼系统提示词（licence 内）
   │                                   ├─ ⑦ SSE 调大模型，最多 8 轮工具调用
   │                                   ├─ ⑧ 模型必须输出固定围栏内的 JSON：
   │                                   │     {名称, 说明, Python代码, 回测参数}
   │                                   ├─ ⑨ 校验五项必填（见下），失败自动重生（≤3次）
   │                                   ├─ ⑩ 提交外部回测平台 Bond-Backtest（HTTP）
   │                                   ├─ ⑪ 轮询回测状态，回收日志/指标
   │  ⑫ 推送助手消息（TEXT→检查中→结果/错误） ◄─┤
   │  ⑬ 我们按版本号轮询，直到拿到代码+终态回测
```

**模型产物的五项必填**（写进系统提示词的硬约束，缺一项会被打回重生）：

1. 债券品种代码；2. 模式（bar/tick/factor）；3. K线周期；4. 开仓条件；5. 平仓条件。

**运行沙箱限制**（生成的策略代码在回测侧执行时）：

- 禁止网络访问、文件读写、`sys`/线程等——**不能在策略代码里拉新闻、调第三方 API**（系统提示词第 49 行明文："不能使用外部数据源（如新闻、经济日历、第三方API等）"）；
- 可用科学计算库：numpy / pandas / scipy / statsmodels / scikit-learn；
- 策略必须继承 KSAPI 的 `StrategyTemplate`，实现 `on_bars` / `on_tick` / `on_factors`。

**这条禁令的边界要分清**：它约束的是**策略代码运行时**不能联网取外部数据；而生成阶段我们在聊天 `content` 里提供市场情报，是平台唯一的正规上下文输入方式，完全合规。因子若要在**回测运行时**被读到，必须提前变成平台认识的数值序列（见 §5）。

## 3. 输入输出契约（使用限制速查）

| 维度 | 限制 | 对我们的影响 |
|---|---|---|
| 输入通道 | 仅聊天消息 `content` 纯文本（协议四字段：模板ID/会话ID/内容/agent） | 舆情、因子、曲线等所有情报必须序列化成结构化文字 |
| 单条长度 | ≤ 10000 token（服务端估算，超出直接报错） | 情报包要做预算管理：摘要 + 表格，不能堆新闻原文 |
| 会话长度 | 每会话 ≤ 50 条消息（代码里的报错文案误写成 20） | 多轮修改要省着用，建议长会话定期开新会话 |
| 并发 | **同一用户同时只能跑一个生成任务**（服务端单飞控制） | 我们后端要排队/加锁，否则第二个请求会被拒 |
| 失败重生 | 校验不过最多自动重新生成 3 次 | 等待时间可能较长，前端要有状态流转 |
| 生成超时 | 我们侧配置 900s；服务端调模型超时 600s | 实测一轮含回测常在 1–5 分钟 |
| 消息类型 | 1 文本 / 2 JSON / 3 Markdown / **4 策略结果** / 5 错误 | 只有 4 是完成信号；**5 是终止信号，我们现在没处理（隐患）** |
| 生成状态 | 1 生成中 / 2 校验回测中 / 3 重生中 / 4 完成 / 5 错误 | 可用于前端状态展示（我们现在只等终态） |
| 回测独立性 | 协议有"单独发起回测"命令（160055） | 后续可用同一版本代码反复调参回测，不必重新生成 |

输出契约（模型围栏 `quantra-strategy-result` 内的单行 JSON）：

```json
{"name": "策略名", "description": "策略说明", "code": "Python StrategyTemplate 代码", "backtest_params": [ ... ]}
```

## 4. 回测是怎么跑的

- DreamStrategy 自己**不算回测**，它把代码 HTTP POST 给外部的 **Bond-Backtest 平台**（线上地址 `http://10.253.50.134/qt`），再轮询 `/status`、取 `/result/info` 与日志。
- 该平台**需要登录令牌（Bearer Token）**：由 DreamStrategy 的 160057 命令按用户写入；近期日志显示 Web UI 使用者（admin）在 10 月 27 日配置过，说明平台本身有人在用。
- 典型回测参数：初始资金 1000 万、Python 语言、策略类型 10001、债券行情源、风控码 47002；回测区间可由模型/参数指定。
- 结果日志含两部分：中文结果块（成交笔数、年化、胜率……）和 Lean 风格 `STATISTICS::` 指标行（Sharpe、Sortino、PSR、Alpha、Beta、回撤等 20+ 项）——我们后端已实现解析。
- **关键口径**：平台只以"回测任务是否成功跑完"（exit code）判定通过；源码注释明确写着 **`total_trade_count=0 is OK`**。也就是说**"0 成交"平台照样判成功**——样本里那个 0 成交策略 `backtest_passed=1`。**"策略必须真实成交"只能靠我们自己把关**（提示词约束 + 回测结果验收 + 带反馈重生）。

## 5. 因子的两条通道（重点）

我们有 381 个非结构化因子（新闻事件流），想让它们影响策略，存在两条本质不同的路径：

### 通道 A：生成期情报（文本，现在就能用，不依赖对方）

因子的**方向、强度、历史命中率、代表事件**写进聊天 content → 影响大模型"写什么策略、定什么条件"。

- 优点：零依赖、当天可上线；策略逻辑里留下的是普通阈值/规则，回测平台都支持。
- 局限：因子只在"生成那一刻"影响策略，**回测过程中策略读不到因子时间序列**；策略里的规则是模型按我们给的情报"翻译"出来的。

### 通道 B：因子数值序列进金仕达因子平台（机器通道，需对方配合）

把事件流构造成**日频因子数值序列**，让 factor 模式策略通过 `on_factors(factor_id)` 在**回测的每个历史时点**读到当时的因子值。已核实存在三个子通道：

| 子路径 | 机制 | 证据 | 依赖 |
|---|---|---|---|
| B1：qfm 因子推送 | 向金工因子平台推送因子元信息和数值（表 `qfm_factor_info`/`qfm_factor_data`，契约含 factor_id、计算时间/公布时间（毫秒）、值类型、因子值） | 金工平台库中存在该推送测试表（目前为空） | 对方提供推送接口/权限与 factor_id 号段 |
| B2：mock_factor HTTP | DreamServer 从 `MOCK_MARKET_BASE_URL/api/v1/mock/standard/query?quotation_type=mock_factor&variety_code=...` 把因子序列拉成"合成 1 分钟 K 线"（区间 2017–2027，JSON 与标准行情兼容） | 源码 `MockMarketHttpSource.cpp/.h`，环境变量默认 `127.0.0.1:20032` | 我们实现这个 HTTP 服务或对方指定地址；策略可像做期货一样用因子序列 |
| B3：回测平台因子文件/FactorHandlerAPI | KSAPI 提供 FactorHandlerAPI，支持因子文件上传读取 | KSAPI 讲解材料、平台因子库（部署明细 2.7 亿条因子计算结果） | 对方给文件格式/上传入口 |

金工因子平台本身生产数据量很大（py_factor_deploy 2.7 万、部署序列 178 万、计算结果 270 万行级），说明机器通道是成熟生产路径，不是摆设。

**构造纪律**（无论哪条子路径）：因子序列必须严格用新闻 `pub_time` 对齐到交易日（防前视）、固定单一抽取模型（在线 GLM；历史回灌模型不同，需分区）、保证回测任意时点只用到"当时已公布"的值。

## 7. 当前真实运行状态（2026-10-28 实测，最需要知道的部分）

### 7.1 服务活着，但几乎没有真实使用

- 进程自 9 月 14 日常驻，端口正常监听；近两天服务端日志只有"列模板""设置回测令牌"（来自 Web UI，客户端 IP 10.253.60.229），**没有真实策略生成**。
- 业务库 `dream_strategy` 里一共 **9 个模板 / 7 个会话 / 19 条消息，全部属于同一测试账号（user_id=3），时间集中在 8 月 11 日–9 月 17 日**。

### 7.2 历史生成样本质量差（实证，不是推测）

| 模板 | 名称 | 回测结果 |
|---|---|---|
| 1 | 期货双均线穿越策略 | exit_code=0 但 **230 个交易日 0 成交、0 收益**；标的选了 **AU2512.SHFE 沪金**（债券平台上的黄金期货），且下单类型误用 `BusinessType.XBOND`（现券买卖类型下到期货上，逻辑错误） |
| 4 | ADX_RSI 波段策略 | 回测失败（exit_code=-1） |
| 2、3、5–9 | 大多无名、未完成 | 多数 exit_code=-1（从未跑出结果） |

9 个模板里仅 1 个"跑通"，而跑通的那个 0 成交且标的/接口错误。**结论：放任模型自由发挥，产出的策略没有使用价值。我们的舆情情报、因子命中率、组合约束恰好是补这块短板的——指定标的、指定模式与周期、给出信号方向和门槛、把"新闻不得单独触发交易"等纪律写死。**

### 7.3 我们配置里的硬伤：模板 ID 不存在

- 我们 `.env`：`DREAM_TEMPLATE_ID=6742a12df19d409396c7384d90e60fa1`。
- 服务端的模板对外 ID 是 32 位十六进制 `open_id`；现存 9 个模板的 open_id 全部与之不同，**这个 ID 在库中（对任何用户）都不存在**。
- 服务端源码确认：创建会话、发消息都执行 `SELECT ... WHERE open_id=? AND user_id=? `，查不到就抛 **"未找到模板"**。
- 我们的后端目前**没有"创建模板"（协议 160050）的调用**，只依赖这个预置 ID。
- ⇒ **在修复之前，我们页面的"确认生成"无法走通**。修复方式二选一：①在 Web UI/数据库侧为我们的登录账号建好专用模板，把 open_id 填入 `.env`；②我们补上 160050 建模板调用，启动时自动确保模板存在。方案文档里列为 M0 第一项。
- 另需核实：门户令牌（config.json 的 publicKey）登录后映射到哪个 user_id——所有模板按用户隔离，必须保证模板归属与登录账号一致。

### 7.4 其他要心里有数的点

- 我们 `DREAM_AGENT=deepseek-chat`，按路由规则走 DeepSeek 官方云端（支持工具调用）；线上 XML 的默认模型写的是阿里 `deepseek-v4-flash`。两者不冲突（消息里带 agent 时以 agent 为准），但"实际由哪个模型出码、licence 是否在有效期内、各渠道额度"建议与对方确认一次。
- 回测令牌（/qt 的 Bearer Token）是**按用户**配的；我们账号是否已配置需要验证，否则会走到回测那一步报 401。
- 我们后端目前**没处理错误消息（类型 5）**：一旦对端报错，现有逻辑会一直等到 900 秒超时而不是立刻把错误返回给用户。

## 8. 对我们项目的意义（怎么定位这次合作）

1. **分工是互补的**：DreamStrategy 强在"会写 KSAPI 代码 + 自动回测 + 版本台账"；它弱在"没有市场观点、乱选标的、拍参数、无法使用舆情"。我们强在舆情结构化、因子与命中率验证、曲线/利差/持仓等市场上下文、组合约束。**我们做策略的大脑，它做代码生成器和回测跑腿。**
2. **产出定位要诚实**：当前没有实盘执行器，链路终点是"**带回测报告的债券策略研究草案（可直接在 Bond-Backtest 复跑）**"。对演示、对投研辅助都有价值；不要对外宣称"自动交易"。
3. **价值保障的四个抓手**（详细工程方案见配套文档）：
   - **标的与五项必填由我们指定**（活跃利率债/国债期货等流动性好的品种，bar 日频为主，匹配小时级舆情频率）；
   - **只用被事件研究验证过的因子**（样本量 n≥20、Wilson 置信区间显著优于多数类基准），并把命中率、样本量、方向、期限随信号一起透明给出；
   - **纪律写死**：舆情只做门控/过滤/确认，不单独触发交易；多空信号冲突时降仓或不交易；严格按 `pub_time` 防前视；
   - **回测验收门**：代码成功只是起点，0 成交、指标异常、与情报方向相悖的结果不通过，带失败原因自动重生并留痕。
4. **分期落地**：M0 先把链路真正跑通（修模板、修错误处理、验证回测令牌）；M1 做强化情报包（纯文本通道，1–2 周可见效）；M2 再推因子数值通道（依赖对方排期）；M3 做"有舆情 vs 无舆情"的增量效果评估闭环。

## 附录 A：术语速查

| 术语 | 含义 |
|---|---|
| 模板（template） | 一个策略的容器，含当前代码版本与回测结果；对外暴露 32 位 open_id |
| 会话（session） | 挂在模板下的一段多轮对话（≤50 条消息） |
| 版本（history/version） | 每次生成的代码快照，版本号递增，可复制、可单独重跑回测 |
| KSAPI | 金仕达策略 API（StrategyTemplate、on_bars/on_factors、买卖下单等） |
| Bond-Backtest / qt | 外部债券回测平台，DreamStrategy 的回测执行方 |
| qfm | 金工因子平台的因子数据推送规范（factor_info + factor_data） |
| mock_factor | 把因子序列伪装成标准 1 分钟 K 线行情的 HTTP 拉取方式 |
| licence | 加密授权文件，内含大模型地址/密钥/系统提示词/API 手册 |
| portal/config.json | 门户公开发现地址：返回 WS 入口 URL 与登录公钥令牌 |
