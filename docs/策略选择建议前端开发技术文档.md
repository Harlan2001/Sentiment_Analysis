# 策略选择建议后端对接文档

## 1. 文档定位

本文档只提供后端能力与对接契约，不包含任何前端技术栈或页面开发指导。

适用对象：任意技术框架的消费方（Web、App、中台、BI、第三方系统）。

- **后端地址**: http://10.253.50.112:8000

---

## 2. 能力概览

策略选择建议服务提供三类能力：

1. 快照查询：拉取当前完整策略快照
2. 手动触发：立即生成一轮新快照
3. 实时订阅：通过 SSE 持续接收完整快照推送

相关接口：

1. `GET /api/strategy/snapshot`
2. `POST /api/strategy/trigger`
3. `GET /api/strategy/sse`

---

## 3. 时间与生成规则

1. 时区：`Asia/Shanghai`
2. 窗口边界：每日 `20:30`
3. 调度频率：每半小时运行一次
4. 窗口起点计算：
   - 若当前时间 >= 当日 20:30，则窗口起点为当日 20:30
   - 若当前时间 < 当日 20:30，则窗口起点为前一日 20:30
5. 每次推送的是完整快照（非增量 diff）

---

## 4. 数据模型

### 4.1 Full Snapshot

```json
{
  "type": "strategy_full_snapshot",
  "generated_at": "2026-05-22 14:30",
  "window_start": "2026-05-21 20:30",
  "items": [
    {
      "run_time": "2026-05-22 10:30",
      "window_start": "2026-05-21 20:30",
      "window_end": "2026-05-22 10:30",
      "status": "success",
      "news_count": 18,
      "strategy": "建议维持中性偏多久期配置，优先关注政策与流动性预期边际变化...",
      "error": null,
      "display_text": "2026-05-22 10:30 交易策略建议：建议维持中性偏多久期配置..."
    }
  ]
}
```

### 4.2 字段定义

顶层字段：

1. `type`：固定值 `strategy_full_snapshot`
2. `generated_at`：快照生成时间，格式 `YYYY-MM-DD HH:mm`
3. `window_start`：当前窗口起点，可能为 `null`
4. `items`：窗口内各时点策略条目数组

`items[]` 字段：

1. `run_time`：本条建议对应运行时点
2. `window_start`：本条建议窗口起点
3. `window_end`：本条建议窗口终点（通常等于 `run_time`）
4. `status`：`success` 或 `failed`
5. `news_count`：本轮参与建议生成的有效新闻条数
6. `strategy`：策略建议正文；失败时可能为空字符串
7. `error`：失败原因；成功时为 `null`
8. `display_text`：服务端拼装的人类可读文本

---

## 5. HTTP 接口契约

## 5.1 GET /api/strategy/snapshot

作用：获取当前完整快照。

请求参数：无。

成功响应：`200 OK`，Body 为 Full Snapshot。

示例：

```bash
curl -X GET "http://<host>/api/strategy/snapshot"
```

---

## 5.2 POST /api/strategy/trigger

作用：立即触发一轮策略生成并返回最新完整快照。

请求头：

1. `Content-Type: application/json`

请求体：

```json
{
  "run_now": true
}
```

响应示例：

```json
{
  "success": true,
  "snapshot": {
    "type": "strategy_full_snapshot",
    "generated_at": "2026-05-22 14:35",
    "window_start": "2026-05-21 20:30",
    "items": []
  }
}
```

说明：

1. 即使触发接口返回成功，消费方仍应以最新快照内容为准。
2. 触发后通常会很快在 SSE 收到下一次完整快照推送。

示例：

```bash
curl -X POST "http://<host>/api/strategy/trigger" \
  -H "Content-Type: application/json" \
  -d '{"run_now": true}'
```

---

## 5.3 GET /api/strategy/sse

作用：实时订阅策略快照。

协议：`text/event-stream`。

事件类型：

1. `strategy_full_snapshot`：`data` 是完整快照 JSON 字符串
2. `ping`：心跳事件，`data` 为 `{}`

事件样例：

```text
event: strategy_full_snapshot
data: {"type":"strategy_full_snapshot","generated_at":"2026-05-22 14:30","window_start":"2026-05-21 20:30","items":[]}

event: ping
data: {}
```

连接行为：

1. 建连后服务端会先推送一次完整快照
2. 无业务更新时周期发送心跳
3. 建议消费方具备断线重连能力

示例：

```bash
curl -N "http://<host>/api/strategy/sse"
```

---

## 6. 状态语义与处理建议

`status=success`：

1. `strategy` 应视为可展示的有效建议
2. `error` 应为 `null`

`status=failed`：

1. `error` 包含失败原因
2. `strategy` 可能为空字符串
3. 消费方可保留最近一条 `success` 作为参考显示

---

## 7. 推荐消费流程（框架无关）

1. 首次进入时调用 `GET /api/strategy/snapshot`
2. 随后建立 `GET /api/strategy/sse` 长连接
3. 收到 `strategy_full_snapshot` 后整体替换本地快照
4. 需要主动刷新时调用 `POST /api/strategy/trigger`
5. 触发后继续等待 SSE 的完整快照作为最终一致结果

---

## 8. 错误处理与健壮性

1. HTTP 非 2xx：按失败处理并记录状态码与响应体
2. SSE data 非法 JSON：忽略该条事件并记录日志
3. SSE 断线：指数退避重连（例如 1s/2s/4s，上限 30s）
4. 重连成功后：以最新 `strategy_full_snapshot` 全量覆盖
5. 时间解析失败：按字符串保留，不阻断消费

---

## 9. 幂等与一致性说明

1. `snapshot` 与 SSE 均为完整快照语义，消费方不依赖增量 patch
2. 同一时点可能收到内容相同的完整快照，属于正常行为
3. 消费方可以 `generated_at + items[].run_time` 作为去重参考

---

## 10. 联调检查清单

1. `GET /api/strategy/snapshot` 能返回合法 JSON
2. `POST /api/strategy/trigger` 能返回 `success=true`
3. `GET /api/strategy/sse` 建连后能收到至少一条 `strategy_full_snapshot`
4. 网络闪断后能自动恢复订阅
5. `status=failed` 场景下 `error` 字段可见且不影响后续恢复

---

## 11. 版本与兼容建议

1. 建议消费方忽略未知字段，避免后续扩展导致解析失败
2. 关键字段建议按必需校验：`type/generated_at/items`
3. 如需强约束，建议在消费侧建立 JSON Schema 并做宽松校验

## 12. 跨域（CORS）配置说明

为支持浏览器直接从前端页面访问本服务，后端已启用 CORS 白名单配置。

说明：

1. CORS 的“来源（Origin）”指前端页面地址（协议 + 主机 + 端口），不是后端 API 地址。
2. 后端地址为 `http://10.253.50.112:8000`，该地址用于接口请求目标，不作为 CORS 来源项。

当前建议配置：

```env
CORS_ALLOW_ORIGINS=http://10.253.50.112,http://localhost:8090,http://127.0.0.1:8090,http://localhost:5173,http://127.0.0.1:5173
```

适用场景：

1. `http://10.253.50.112`：部署环境前端页面来源
2. `http://localhost:8090`：本地开发机（Vue dev server）调试来源
3. `http://127.0.0.1:8090`：本地开发机等价调试来源
4. `http://localhost:5173`：本地开发机（Vite）调试来源
5. `http://127.0.0.1:5173`：本地开发机等价调试来源

开发态说明：

1. 若前端通过本地 dev server 代理 `/api` 到后端（同源访问），浏览器请求通常不依赖后端 CORS。
2. 若前端改为浏览器直接访问 `http://10.253.50.112:8000`，则必须命中后端 CORS 白名单。

当前后端放行策略：

1. Methods：已放行全部（包含 `GET`、`POST`、`OPTIONS`）
2. Headers：已放行全部（包含 `Content-Type`、`Authorization`、`Accept`）

注意事项：

1. 若前端实际访问端口不是 80（例如 `:8080`），需将对应来源追加到 `CORS_ALLOW_ORIGINS`。
2. 修改 `.env` 后需重启后端进程或容器方可生效。
