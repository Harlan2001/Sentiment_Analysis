## 4. 推荐目标架构（SaaS版）

### 4.1 数据链路

1. Spider 抓取新闻（外部项目）。
2. Ingest API 接收并做去重校验（global_uid 或 source+source_news_id）。
3. 写入 news/news_content_blocks。
4. 发布消息到队列（news_created 事件）。
5. 分析 Worker 消费消息：
   - 向量化
   - 因子匹配
   - 情绪/方向分析
   - 结果写入 analysis/news_factor/news_vectors
6. API 查询层提供多视图输出（best/single/all）。

### 4.2 控制链路

1. 调度器负责兜底批处理（补偿未处理数据）。
2. 队列负责实时触发（主路径）。
3. 重试与死信队列负责异常数据回放。

你当前已有日调度能力和分析执行器，适合在此基础上加“消息队列触发”。

## 5. 上线必须补齐的能力清单

## A. 数据接入层

1. 入库幂等：重复消息不重复入库。
2. 字段规范：时间统一为 UTC 存储 + 本地时区展示。
3. 数据质量校验：标题为空、正文异常、时间逆序要拦截。
4. 来源治理：source 白名单、来源配额、来源健康度评分。

## B. 实时处理层

1. 事件驱动：新增新闻触发分析任务。
2. 任务状态机：PENDING/RUNNING/SUCCEEDED/FAILED。
3. 重试策略：指数退避 + 最大重试次数 + 死信。
4. 并发限流：按模型供应商和租户做 QPS 控制。

## C. 模型与结果层

1. 模型版本化：记录 model_name + prompt_version + pipeline_version。
2. 可追溯性：每条结果可追溯到原始新闻与处理日志。
3. 回放能力：支持按时间段或批次重新分析。
4. 结果一致性：同新闻多模型冲突时有优先级规则。

## D. SaaS 平台层

1. 多租户隔离：逻辑隔离（tenant_id）或物理隔离（库/表）。
2. 鉴权授权：API Key + RBAC。
3. 限流配额：按租户控制调用频率和额度。
4. 账单计量：记录请求次数、token 消耗、数据量。

## E. 运维与安全层

1. 监控看板：延迟、吞吐、失败率、队列积压、模型耗时。
2. 告警机制：延迟超阈值、失败率升高、无数据输入。
3. 容灾备份：数据库备份、索引备份、跨可用区策略。
4. 合规审计：敏感信息脱敏、访问审计、操作留痕。

## 7. 分阶段上线建议

## Phase 1（2-3 周）：先“可上线”

1. 明确时效 SLO（先选 T1：10-30 分钟）。
2. 建立 news_created 事件队列 + 分析 Worker。
3. 增加任务状态表与失败重试机制。
4. 补充监控和基础告警（延迟/失败率/积压）。

产出：能稳定跑、延迟可控、异常可恢复。

## Phase 2（3-5 周）：再“可运营”

1. 模型版本与回放机制。
2. 多租户鉴权与限流。
3. 账单计量与用量报表。
4. 完整运维手册和上线回滚方案。

产出：具备正式 SaaS 交付能力。

## Phase 3（持续）：做“可增长”

1. 快慢轨分层优化成本。
2. 自动化评估体系（准确率、稳定性、成本）。
3. 客户分层 SLA（标准版/专业版）。

## 8. 给你的直接建议（回答“每分钟还是每小时”）

不建议二选一，建议分层：

1. 关键来源与关键因子：分钟级（1-3 分钟）。
2. 全量新闻补齐：小时级（30-60 分钟）。
3. 每日离线校准：日级（如 12:00 批处理）做补偿与修正。

这样既满足交易敏感场景，也保证总体成本和稳定性。

---

## 9. 最小上线验收标准（Checklist）

1. 新增新闻 95% 在 30 分钟内完成分析并可 API 查询。
2. 单条新闻处理失败可自动重试，最终失败进入死信并可人工回放。
3. API 可用率达到 99.9%，有告警闭环。
4. 模型输出可追溯到输入新闻、模型版本和处理日志。
5. 有完整上线回滚方案与数据备份恢复演练记录。

满足以上 5 条，再对外承诺 SaaS 上线更稳妥。
