# 舆情因子调用 DreamStrategy 生成策略——简明实施说明

> 状态：待审核，审核通过前不修改功能代码  
> 日期：2026-10-29  
> 实施范围：只修改 `Sentiment_Analysis` 项目，不修改 DreamStrategy 的 C++ 源码，不重写现有前端和接入协议。

## 一、我们到底要做什么

一句话：**把 Sentiment 的新闻和因子整理成一份“策略情报包”，交给 DreamStrategy 生成 Python 策略并回测，最后把合格的代码和回测结果展示给用户。**

两个系统各做自己擅长的事：

- **Sentiment 负责提供依据**：最近发生了什么、哪些因子被触发、方向是什么、历史表现是否可靠。
- **DreamStrategy 负责生成和执行研究代码**：把明确的需求转成 KSAPI Python 策略，并调用 Bond-Backtest 回测。
- **Sentiment 再负责验收**：回测跑完不代表策略合格，没有真实成交、标的错误或者回测失败，都不能当作成功结果。

最终交付物是“**带因子依据和回测报告的策略研究草案**”，不是实盘自动交易系统。

## 二、完整链路

```text
用户提出策略需求
        ↓
Sentiment 读取近期新闻、因子事件和因子历史表现
        ↓
筛选可靠因子，生成“策略情报包 + 明确交易任务”
        ↓
通过现有 WebSocket + Protobuf 接口发给 DreamStrategy
        ↓
DreamStrategy 大模型生成 KSAPI Python 策略
        ↓
DreamStrategy 调用 Bond-Backtest 回测
        ↓
Sentiment 取回代码、日志和指标，并检查是否真正合格
        ↓
保存输入依据、生成代码和回测结果，在现有页面展示
```

这里最重要的一点是：**本期因子是在“生成策略时”作为文字情报传给大模型，不是让生成后的策略在回测过程中调用 Sentiment API。**

原因是 DreamStrategy 的聊天文本已经有正式输入通道，而策略回测环境不应访问新闻或第三方 API。若以后要让策略在每个历史交易日读取因子数值，需要再建设因子时间序列通道，见本文第八节。

## 三、现在已经有什么，不需要重做

当前 Sentiment 已经具备以下能力：

1. 用户创建策略会话，先看到提示词草稿，再点击确认生成。
2. 后端能够连接 DreamStrategy、创建远端会话、发送提示词、接收正式策略版本。
3. 后端能够取得策略代码、回测日志和多项回测指标。
4. 生成记录、代码和结果已经会保存，现有页面每 4 秒查询并展示进度和结果。
5. 当前提示词已经包含近期代表新闻、新闻方向、收益率曲线和正负向因子名称。

所以这次不是从零开发，而是**在现有链路上补全信息、修复阻断点并增加质量检查**。

## 四、当前需要解决的主要问题

1. **远端模板不可用**：当前配置的 DreamStrategy 模板 ID 在对端不存在，会阻断正式生成。
2. **因子信息太简单**：底层虽然已经查出因子代码、方向、事件数等信息，但实际发给 DreamStrategy 的基本只有因子名称，缺少历史命中率、基准和样本量。
3. **模型自由度过大**：现有提示词仍让模型自行选择具体标的，容易选错资产或使用不匹配的下单接口。
4. **缺少账号级排队**：DreamStrategy 同一个账号同时只能执行一个 AI 生成任务；当前只限制了单个本地会话，不同会话仍可能同时提交。
5. **远端错误不能立即结束**：接收循环只把策略结果当作终态，没有直接处理对端错误消息，可能一直等到超时。
6. **没有成交验收**：当前主要根据退出码和日志判断回测完成，没有要求真实成交，因此“0 成交”也可能被保存成成功策略。

## 五、具体怎么做

### 第 1 步：先保证每次都能进入正确的 DreamStrategy 模板

- 优先使用为我方账号准备好的专用模板；如果允许自动创建，则调用 DreamStrategy 已有的 `160050` 接口创建。
- 将模板 ID、会话 ID 与本地策略会话关联保存，后续生成继续复用，避免所有策略混在一个远端模板里。
- 联调时同时确认登录账号、模板归属和 Bond-Backtest 回测令牌，确保不是只生成代码而没有真正回测。

### 第 2 步：把因子整理成一张简明的“信号面板”

不把 381 个因子全部塞给模型，只选择近期有事件、且历史样本相对可靠的因子。首版建议：

- 固定使用同一个分析模型；在线生成默认使用 `glm`，不与 `doubao`、`deepseek` 混算。
- 历史样本量建议不少于 20，并优先选择命中率高于多数类基准的因子。
- 最多选择 8 个，避免提示词过长和噪声过多。
- 每个因子提供：代码、中文名、方向、近期事件数、净方向、最近触发时间、历史命中率、多数类基准、样本量和持有期。
- 附上少量代表性新闻及传导理由，解释因子为什么可能影响债市。
- 如果没有合格因子，就明确写“当前证据不足”，不硬凑交易信号。

因子方向必须写清楚：**`positive` 表示利多中国国债、收益率下行；`negative` 表示利空中国国债、收益率上行。**不能直接把这套方向套到黄金、股票等其他资产上。

### 第 3 步：把用户要求变成明确的“策略任务卡”

Sentiment 在提示词中明确给出：

- 交易标的或标的白名单；
- 策略模式和频率，首版以 `bar` 日频为主；
- 回测区间和初始资金；
- 开仓、平仓的基本规则；
- 仓位、止损和冲突处理要求；
- 因子只能用于方向确认、交易过滤或风险降级，不能单独触发交易。

这样做是为了让大模型主要负责“把明确规则写成正确代码”，而不是替我们随意选择标的和投资逻辑。具体标的和回测区间由产品或策略人员确认后设为默认值，用户可在允许范围内修改。

### 第 4 步：复用现有接口生成并回测

继续走现有 `DreamClient` 和 `generate_strategy()`，不新增第二套客户端：

1. 登录并创建或复用远端会话。
2. 发送“策略任务卡 + 因子信号面板 + 市场信息”。
3. 等待正式策略版本，而不是把普通聊天文本当成结果。
4. 取得代码、回测日志和指标。

同时补充两项保护：

- 同一 DreamStrategy 账号的生成请求串行执行，其余请求显示“排队中”。
- 收到对端错误消息后立即返回明确原因，不再无意义地等待到超时。

### 第 5 步：Sentiment 增加自己的验收门

只有同时满足以下条件，才把本次任务标记为成功：

- 有完整策略代码和策略说明；
- 回测确实执行完成，回测通过标志和退出码正常；
- 回测日志和关键指标能够取得；
- 有真实成交，不能只满足“程序跑完了”；
- 标的与任务卡一致，下单方式与标的类型匹配。

不合格时，页面应明确显示“回测失败”“无成交”或“标的不符合要求”，不能展示为成功。后续可将失败原因和少量回测摘要发回原会话重试，最多两轮，并保留每轮结果。

### 第 6 步：保存依据并复用现有页面展示

每次生成保留以下快照：用户需求、因子面板、代表新闻、提示词版本、远端模板和会话、生成代码、回测日志、指标、验收结果及失败原因。

首版继续使用现有页面轮询，不必为了实时推送重做前端。只需补充“排队中、生成中、回测中、验收失败”等必要状态和原因展示。

## 六、审核通过后预计修改的位置

| 位置 | 要做什么 |
|---|---|
| `backend/integrations/dream/client.py` | 补充创建远端模板所需的协议命令 |
| `backend/integrations/dream/service.py` | 模板确保、远端错误终态、账号级串行、回测与成交验收 |
| `backend/strategy/sentiment_context.py` | 查询并组装带历史表现的因子信号面板 |
| `backend/strategy/dream_strategy_prompt.py` 及现有提示词模板 | 加入策略任务卡、因子面板和明确验收要求 |
| `backend/routers/ai_strategy_generation.py` 及现有历史仓储 | 保存完整输入快照、验收状态和必要进度 |
| 现有策略页面 | 仅补状态和失败原因展示，不重做页面 |
| `tests/` | 补模板、错误终态、串行、无成交拒绝和提示词内容测试 |

具体表结构优先复用现有会话、消息和版本表；只有现有字段确实无法保存时，才增加必要字段或迁移脚本。

## 七、第一期怎么算完成

用一个明确的债券策略需求完整验收：

1. 页面能看到本次使用了哪些因子，以及每个因子的方向、命中率和样本量。
2. 点击确认后，DreamStrategy 能生成指定资产范围内的策略，不再随意选错标的。
3. Bond-Backtest 确实完成回测，页面能显示代码、日志和指标。
4. 回测有真实成交；无成交时不会被标记为成功。
5. 对端报错能及时显示；连续提交两个任务时，第二个会排队。
6. 事后能够还原“当时给 DreamStrategy 的完整输入”和“最终得到的结果”。

## 八、本期不做什么，后续再扩展

本期先打通“**因子文字情报 → 策略生成 → 回测验收**”链路，暂不让策略在回测运行时读取因子时间序列。

后续如果证明一期链路有价值，再单独立项实现：

1. 将因子事件按 `pub_time` 转成日频数值面板，严格防止未来函数。
2. 通过金仕达认可的 qfm、因子文件或其他正式通道提供因子值。
3. 让 `factor` 模式策略通过 `on_factors` 在历史每个时点读取当时已经公布的值。
4. 对比“使用因子门控”和“不使用因子门控”的回测差异，验证因子是否真正带来增量。

这部分依赖金仕达提供因子通道和编号，不作为本次最小交付的前置条件。

## 九、开发前需要确认的三个业务问题

1. 第一条示范策略使用什么标的和回测区间，是否先固定为流动性较好的国债或国债期货日频策略。
2. 我方使用哪个 DreamStrategy 登录账号和专用模板，该账号是否已配置有效的回测令牌。
3. 是否认可本期先交付“生成期因子情报链路”，将回测运行期因子数值通道放到后续阶段。

以上三点确认、本文审核通过后，再开始修改 Sentiment 功能代码。
